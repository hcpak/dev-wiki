# AI에게 작업을 맡기려면, 완료의 기준부터 만들어야 했다

AI에게 맡기는 일이 늘었다. 코드를 작성하고 수정하는 일뿐 아니라 테스트를 실행하고, 성능을 측정하고, 결과를 정리하는 일까지 맡겼다.

그만큼 내가 확인해야 할 결과도 늘었다. AI가 “테스트를 통과했다”고 하면 어떤 조건으로 실행했는지 다시 물었다. 결과가 이상하면 로그를 확인하게 하고, 빠진 검사가 보이면 추가로 지시했다.

하나씩 확인할 때는 괜찮았다. 하지만 여러 작업이 이어지자 요청과 피드백만으로 모든 과정을 따라가기 어려워졌다. 일을 맡기고도 그 일이 제대로 됐는지 확인하는 데 계속 붙어 있어야 했다.

그래서 고민이 바뀌었다.

**내가 매번 확인하지 않아도, 잘못된 실행을 걸러낼 수 있게 만들 수는 없을까?**

여러 서버에서 부하 테스트를 진행하면서 이 질문을 구체적으로 다뤄 봤다. 실행 절차를 코드로 만드는 데서 한 걸음 더 나아가, 어떤 결과를 받아들일지 판단하는 검사도 코드에 넣었다. 그러자 요청이 모두 성공한 실행을 통과로 인정하지 않는 일이 생겼다.

## 지시를 더 자세히 하는 것만으로는 부족했다

이번에 확인하려던 것은 로드밸런서가 많은 연결을 받아 처리할 수 있는지였다. 로드밸런서는 들어온 트래픽을 뒤쪽 서버로 전달한다. 많은 요청을 보내면서 응답이 느려지거나 실패하는지 보는 실험을 부하 테스트라고 한다.

요청을 보내는 서버 한 대만으로는 원하는 부하를 만들기 어려워 가상 서버 8대를 사용했다.

```text
요청을 만드는 서버 8대 → 로드밸런서 → 응답하는 서버
      부하를 보내는 쪽       측정 대상      응답하는 쪽
```

여기서는 요청이 성공했는지만 보면 부족하다. 8대가 같은 시간대에 부하를 보내야 합쳐서 목표한 부하를 만들 수 있다. 일부 서버가 늦게 시작하거나 중간에 충분한 요청을 보내지 못하면, 측정 대상은 우리가 의도한 것보다 다른 부하를 받게 된다.

AI에게 “여러 서버에서 동시에 실행해 줘”라고 지시해도 의문은 남았다. 명령만 동시에 보낸 것인지, 실제 부하도 함께 시작됐는지 알 수 없었다.

측정 절차를 코드로 만들면 이 문제가 해결될 것 같았다. 실행 방법과 설정이 남으니 다시 확인하기 쉬워진 것은 맞았다. 하지만 **코드가 실행됐다는 사실만으로 원하는 조건이 만들어졌다고 볼 수는 없었다.** 그 코드도 잘못된 절차를 반복할 수 있었다.

## 내가 확인하던 질문을 검사로 옮겼다

그래서 실행 전에 ‘어떤 조건을 충족해야 이번 측정 결과를 사용할 수 있는가’를 정리했다. 막연하게 “잘 실행해 줘”라고 맡겼던 부분을 확인 가능한 질문으로 바꿨다.

| 내가 확인하고 싶었던 것 | 남기거나 검사한 것 |
|---|---|
| 정말 8대가 이번 실행에 참여했나? | 서버별 실행 식별자, 완료 기록, 종료 상태 |
| 함께 부하를 보내기 시작했나? | 서버별 실제 시작 시각과 시계 오차 |
| 설정한 만큼 꾸준히 보냈나? | 모든 서버가 함께 동작한 구간의 서버별 초당 부하 |
| 요청이 측정 대상을 거쳤나? | 요청을 보낸 쪽·로드밸런서·응답하는 쪽의 기록 |

시작 시각 차이와 부하 속도에는 허용 범위를 두었다. 숫자는 이번 실험의 조건에 맞춰 정했고, 결과가 나온 뒤 통과시키기 위해 넓히지 않았다.

이 기준과 기록을 측정·검증 코드에 넣었다. 서버가 빠지거나 기록이 누락된 실행, 실제 부하가 기준을 벗어난 실행을 성공 건수만 보고 통과시키지 않도록 했다. 각 실행의 코드와 설정, 원본 로그도 함께 남겼다.

이렇게 하니 AI의 설명을 읽으며 내가 하나씩 다시 물어보던 내용 중 일부를, 실행할 때마다 같은 방식으로 확인할 수 있게 됐다.

## 성공처럼 보이는 결과를 실제로 걸러냈다

첫 실행에서는 요청 72,000건이 모두 성공했다. 실패가 없으니 다음 단계로 넘어가도 될 것처럼 보였다.

그런데 시작 시각 검사가 통과하지 못했다. 시계 오차까지 고려한 서버 간 시작 편차의 상한이 약 1.18초로, 정해 둔 1초 기준을 넘었다.

이 실행은 ‘무효’로 남겼다. 요청이 성공했다는 관측을 버린 것은 아니다. **이번 실험의 조건을 충족한 결과로 사용하지 않았다는 뜻**이다.

기존 절차는 정해진 시각에 부하 도구를 실행했다. 하지만 프로그램이 뜨고 준비되는 시간은 서버마다 달라질 수 있었다. 부하 도구를 미리 띄워 두고 예약 시각까지 기다리도록 바꾼 뒤, 실제 시작 기록을 다시 검사했다. 재실행에서는 기준을 충족했다.

다음 단계에서도 요청은 모두 성공했지만 다른 검사가 문제를 잡았다. 한 서버가 매초 부하를 보내는 속도가 허용 범위를 벗어났다.

전체 건수만 봤다면 놓쳤을 문제다. 잠깐 적게 보내고 다음 순간 몰아서 보내도 합계는 비슷할 수 있다. 일정한 부하를 확인하려면 시간별로 보낸 양도 봐야 했다.

이 실행 역시 통과로 인정하지 않았다. 같은 설정으로 한 번 더 실행한 결과는 통과했지만, 앞선 기록도 보존했다. 통과한 결과만 남기면 부하를 만드는 쪽이 불안정했던 사실을 놓치기 때문이다.

여기서 변화가 분명해졌다. ‘실패 0건’이라는 요약을 보고 내가 다시 의심해야만 찾을 수 있었던 문제가, 미리 넣어 둔 검사에서 드러났다.

## 검사 코드도 AI가 만들었다면 무엇을 믿을까?

검사를 코드로 만들었다고 의심이 모두 사라진 것은 아니다. 검사 코드 역시 AI가 작성했다. 부하를 만드는 코드와 검사하는 코드가 같은 가정을 공유하면 함께 틀릴 수도 있다.

그래서 결과를 한 곳의 보고로만 판단하지 않으려 했다. 최종 실행에서는 부하를 보내는 쪽이 성공으로 기록한 352,000건을 다른 지점의 기록과 맞춰 봤다.

| 관측 지점 | 확인한 기록 |
|---|---|
| 부하를 보내는 쪽 | 성공 요청 352,000건 |
| 로드밸런서 | 사전 확인용 트래픽을 제외한 연결·세션 카운터가 각각 352,000 증가 |
| 응답하는 쪽 | 실험 전용 URL의 성공 응답 로그 352,000건 |

숫자를 대조할 때도 주의가 필요했다. 연결 수와 요청 수는 언제나 같지 않다. 하나의 연결로 여러 요청을 보낼 수 있기 때문이다. 각 기록이 무엇을 세는지와 비교 구간을 함께 봐야 한다.

이번에 확보한 것은 해당 실행 구간의 건수가 일치한다는 증거다. 모든 패킷의 이동을 추적한 것은 아니다. 그래도 로드밸런서 CPU가 올라갔다는 사실만 확인했을 때보다, 요청이 처리된 경로를 설명할 근거가 늘었다.

원본 로그를 남긴 것도 같은 이유다. 요약이나 검사 코드에 문제가 발견되면 같은 실행의 기록으로 다시 판단할 수 있어야 했다. 실제로 마지막 로그 수집이 실패했을 때도, 남아 있던 원본을 회수해 검증을 마칠 수 있었다.

## 무엇을 맡기고, 무엇을 계속 판단해야 할까?

이번에 코드로 옮긴 것은 반복해서 확인할 수 있는 부분이었다. 어떤 서버가 실행됐는지, 실제 부하가 범위 안에 있었는지, 관측 건수가 일치하는지 같은 검사다.

여전히 판단이 필요한 부분도 있었다. 시작 편차를 어느 정도 허용할지, 얼마나 오래 실행해야 충분할지, 어떤 기록을 결과의 근거로 삼을지는 측정 목적에 따라 달라진다. AI가 제안할 수는 있지만, 실행이 통과했다는 이유로 그 기준 자체까지 적절했다고 결론낼 수는 없다.

결과를 해석하는 범위도 남았다. 최종 부하 단계는 한 번 통과했을 뿐이다. 장시간 안정성이나 최대 처리량을 확인한 것은 아니다. 한 서버에서는 연결 시도 재전송 카운터도 증가했는데, 서버 전체 값이라 이번 테스트와 관련된 증가인지 단정할 수 없었다.

그래서 이번 결과는 ‘이 조건에서 한 차례 실행이 부하 기준과 건수 대조를 통과했다’는 범위로 남겼다. 확인하지 못한 것을 함께 적어야 다음에 할 실험도 정할 수 있었다.

## 작업과 함께, 완료를 판단하는 방법도 준비하기

처음에는 AI에게 지시를 더 자세히 하고 피드백하면 결과를 믿을 수 있을 거라고 생각했다. 하지만 작업이 늘어날수록 내가 모든 과정을 확인하는 방식은 버거워졌다.

이번에는 확인해야 할 조건을 코드로 남겼다. 그러자 요청이 모두 성공한 실행도 조건에 맞지 않으면 걸러낼 수 있었다. 매번 내가 결과를 의심하고 추가 질문을 해야 찾을 수 있던 문제 중 일부를, 반복 가능한 검사로 옮긴 셈이다.

**이제 AI에게 작업을 맡길 때는 ‘무엇을 해 달라’와 함께 ‘무엇을 확인해야 완료로 인정할 수 있는가’를 준비하려 한다.**

성능 측정이라면 다음처럼 요청할 수 있다.

> 실행 전에 이 실험으로 확인하려는 것과 통과 조건을 정리해줘. 실행 후에는 설정값과 실제 부하를 비교하고, 다른 관측 지점의 기록과 대조해줘. 조건을 벗어난 실행은 별도로 표시하고, 원본과 확인하지 못한 항목도 남겨줘.

요청문만으로 해결되는 일은 아니다. 그 조건이 목적에 맞는지 검토하고, 실제로 검사할 수 있는 코드와 증거가 있어야 한다.

그 환경을 만들었다고 AI를 무조건 믿게 된 것은 아니다. 다만 어떤 근거로 결과를 받아들였는지, 무엇을 아직 모르는지 설명할 수 있게 됐다. 이번 실험에서 얻은 가장 큰 변화는 성능 수치보다, **사람이 계속 지켜보며 확인하던 일부 판단을 실행 과정 안에 넣었다는 것**이었다.

다음 글에서는 이 질문을 테스트 코드로 옮겨 보려 한다. AI가 구현과 테스트를 모두 작성한다면, 둘이 같은 오해를 공유하는 경우는 어떻게 찾아낼 수 있을까?

## 실험 기록: 조건과 전체 결과

아래는 본문의 판단을 확인하고 싶은 독자를 위한 상세 기록이다. 수치는 이번 실험의 기준이며 다른 서비스에 그대로 적용할 기본값은 아니다.

### 구성과 판정 기준

- 부하 도구: Gatling 3.3.1, 가상 서버(VM) 8대, 응답 크기 5KB.
- 목표 단계: 8대 합계 초당 가상 사용자 시작 수 2,000 → 5,000 → 10,000. 최종 VM당 초당 가상 사용자 시작 수 1,250.
- 부하 증가 10초, 유지 30초. 공통 유지 구간 최소 20초.
- 시계 오차의 추정 상한 0.25초, 실제 시작 편차 상한 1초.
- 공통 유지 구간에서 VM별 매초 부하 속도는 목표의 95~105%.

Gatling의 가상 사용자 시작 기록과 HTTP 요청 시작 기록을 따로 검증했다. 목표로 삼은 CPS(초당 연결 수)와 도구에 설정한 가상 사용자 시작 수는 구분해야 한다. 이번 실험에서 초당 TCP 연결 도착률을 패킷 단위로 직접 측정한 것은 아니다.

### 무효 회차를 포함한 결과

| 목표 가상 사용자 시작 수(/초, 8대 합계) | 실행 | 성공 / 실패 | 서버별 p99 중 최댓값 | 판정 |
|---|---|---:|---:|---|
| 2,000 | 첫 실행 | 72,000 / 0 | 5ms | 무효: 시작 편차 초과 |
| 2,000 | 시작 절차 수정 후 | 72,000 / 0 | 5ms | 통과 |
| 5,000 | 첫 실행 | 177,000 / 0 | 7ms | 무효: 부하 속도 이탈 |
| 5,000 | 동일 조건 재실행 | 177,000 / 0 | 8ms | 통과 |
| 10,000 | 첫 실행 | 352,000 / 0 | 54ms | 통과 |

p99는 관측한 응답 시간의 99%가 그 값 이하였다는 뜻이다. 표에는 각 부하 서버에서 계산한 p99 중 가장 큰 값을 적었다. 예를 들어 54ms는 8대의 요청을 모두 합쳐 계산한 p99가 아니라, 서버별 p99 중 최댓값이다.

첫 실행의 시작 편차 상한은 1.177초, 시작 절차 수정 후에는 0.660초였다. 5,000 단계의 무효 회차에서는 특정 VM의 초당 부하 속도가 목표 625에 대해 591~658로 흔들렸고, 공통 구간에서 최대 60ms의 가상 사용자 주입 공백이 관측됐다. 원인은 확정하지 못했다.

최종 실행에서는 서로 다른 boot ID 8개, VM별 정상 종료와 요청 44,000건을 확인했다. 공통 유지 구간 26초에서 총 가상 사용자 시작률은 초당 9,979~10,020, 평균 약 9,999.5였다. VM별 HTTP 요청 시작률도 기준을 충족했다.

### 증거의 범위와 수집 과정

로드밸런서 frontend 연결·backend 세션 카운터 대조에서 사전 확인 요청 80건을 제외했다. 응답 서버에서는 실험 전용 URL의 로그를 확인했다. 로드밸런서와 응답 서버 시계의 독립적인 오차 상한은 측정하지 않았으므로, 건수 대조를 정밀한 패킷 시간 추적으로 해석하지 않는다.

한 VM의 호스트 전체 TCPSynRetrans와 TCPTimeouts 카운터가 각각 426 증가했다. 해당 테스트 경로의 문제인지와 원인은 미확정이다.

부하 완료 후 관리용 SSH 타임아웃으로 마지막 로드밸런서 로그 수집이 실패했다. 부하를 재실행하지 않고 동일 실행의 원본 로그를 회수해 연속성과 건수를 재검증했다. 드라이버의 실패 종료 기록도 보존했으며, 결과 상태는 ‘수집 복구 후 검증 완료’다.
