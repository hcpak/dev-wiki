# expect 스크립트가 느릴 때 — 어느 `expect`가 timeout을 태우는가

> expect 자동화가 "명령은 끝났는데 한참 멈춰 있다"면, 대개 **패턴이 안 맞은 `expect` 하나가
> 전역 `set timeout` 을 통째로 소진**하는 것이다. 총 소요가 timeout 값과 거의 같으면 확정적이다.

## 왜 그렇게 동작하나

`expect`는 패턴이 나타날 때까지 기다린다. `timeout` 분기를 적어두지 않으면,
시간이 다 되어도 **에러 없이 조용히 다음 줄로 넘어간다**. 그래서 증상이 "실패"가 아니라 "느림"으로 나타난다.

```tcl
set timeout 90          ;# 전역 기본값

# ... 로그인, 명령 실행 ...

send "exit\r"
expect -glob {[$#]}     ;# timeout 분기 없음 → 안 맞으면 90초 통째로 소진
expect eof              ;# 여기도 마찬가지
```

패턴이 어긋나는 흔한 이유는 **앞선 `expect`가 패턴을 먼저 먹어버리는 것**이다.

```tcl
send "$cmd\r"
expect -glob "#"        ;# 프롬프트의 # 를 기다리는 의도지만…
```

`#`는 한 글자짜리 패턴이라, 명령 자체의 에코나 출력 안에 `#`가 있으면 **거기서 매칭이 끝난다.**
그러면 한 칸씩 밀려서 마지막 `expect`가 짝을 잃고 timeout까지 간다.
같은 원인으로 **명령 출력이 중간에서 잘리는** 버그도 함께 생긴다.

## 확인하는 방법

추측하지 말고 **단계마다 타임스탬프를 찍은 사본**을 만들어 재보면 한 번에 나온다.

```tcl
puts stderr "[clock milliseconds] STAGE C wait-prompt"
```

```
STAGE A spawn
STAGE B gateway-login    +0.1s
STAGE C wait-prompt      +0.3s
STAGE D ssh-target       +0.0s
STAGE E runuser          +0.5s
STAGE F exec-cmd         +0.0s   ← 실제 작업은 여기서 끝
STAGE G exit1            +0.0s
STAGE H final            +0.0s
STAGE I before-eof       +90.0s  ← 범인
STAGE J after-eof        +0.1s
```

로그인부터 명령 완료까지 1초 미만이고, **종료 처리에서 90초**를 태우고 있음이 드러난다.
`+90.0s`가 전역 timeout 값과 일치하는 것이 결정적 단서다.

`time` 으로 총 소요만 재도 1차 판별은 된다. CPU 사용률이 0%에 가까우면 순수 대기다.

```
0.05s user 0.03s system 0% cpu 1:32.58 total     ← 92.6초 ≈ 90초 + α
```

## 함정

- ⚠️ **`timeout` 분기가 없는 `expect`는 실패해도 조용하다.** 에러 메시지가 없다고 정상인 것이 아니다.
- 한 글자 패턴(`#`, `$`)은 프롬프트 매칭용으로 위험하다. 출력에 그 글자가 있으면 오매칭된다.
  근본 해결은 **원격 셸이 확장하는 종료 마커**를 쓰는 것이다.

  ```tcl
  send "$cmd; echo done_\$\$_end\r"          ;# $$ 를 이스케이프해 리터럴로 보낸다
  expect -re {done_[0-9]+_end}
  ```

  **왜 `$$` 인가**: 보낸 줄은 터미널에 그대로 되비치므로(에코) 마커 문자열이 **두 번** 나타난다.
  에코에 먼저 걸리면 아무 출력도 못 받고 넘어간다. `$$` 를 쓰면 에코에는 리터럴 `$$` 가 남고
  실제 실행 결과에만 PID 숫자가 들어가므로, `[0-9]+` 를 요구하는 정규식이 **에코를 자동으로 걸러낸다.**

  ⚠️ "마커를 두 번 기다린다"(에코 1회 + 결과 1회)로 해결하려는 방법은 **에코가 깨지는 환경에서 실패한다.**
  중간 장비를 여러 단 거치면 에코에 글자가 중복되어 나타나는 일이 있어(`hostname` → `hosstname`)
  에코 자체를 매칭 대상으로 삼으면 안 된다.

  마커는 명령 **뒤**에 붙이고 `&&` 가 아니라 `;` 로 잇는다. `&&` 면 명령이 실패했을 때 마커가 나오지 않아
  그대로 timeout을 태운다.

- 최소 수정으로 급한 불만 끌 때는 **종료 구간 직전에만 timeout을 낮춘다.** 명령 실행 대기는
  길게 유지해야 하므로 전역 값을 건드리면 안 된다.

  ```tcl
  set timeout 5      ;# 종료 처리에만 적용
  send "exit\r"
  expect -glob {[$#]}
  ```

- 세션 종료가 느린 것이 **서버측 사정**일 수도 있다(세션 녹화 종료, 로그 변환 등).
  그 경우 timeout을 줄이는 것은 "기다리지 않기로 하는" 선택이지 서버를 고치는 게 아니다.
  다만 자동화 입장에서는 대개 그걸로 충분하다.

## 관련

- 원격 다단계 접속(게이트웨이 → 대상 호스트 → 권한 상승)은 단계마다 `expect`가 필요해
  이 문제가 누적되기 쉽다.
