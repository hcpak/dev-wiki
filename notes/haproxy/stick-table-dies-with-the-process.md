# stick-table 은 프로세스 메모리다 — 리로드에서 옛 프로세스를 죽여 얻는 것은 연속성이 아니라 일관성

> `-sf` 리로드는 새 haproxy 가 먼저 포트를 넘겨받고, 옛 프로세스는 기존 연결을 마무리할 때까지 남는다.
> 연결은 안 끊기지만 **`stick on src` 의 stick-table 은 새 프로세스로 넘어가지 않는다**(peers 가 없으면).
> 두 프로세스가 공존하는 동안 같은 클라이언트의 기존 연결(옛 테이블 → 멤버 A)과 새 연결(빈 테이블 → 알고리즘이
> 고른 멤버)이 갈라질 수 있다(추정, 직접 관측 전). 새 프로세스를 띄운 직후 옛 프로세스를 kill -9 하면 이 창은
> kill 시점까지로 줄어들지만 "리로드 전과 같은 멤버"는 보장되지 않는다 — 첫 요청은 밸런싱 알고리즘, 두 번째부터
> 테이블이다. 실측 범위에서 테이블이 새 프로세스로 넘어간 경로는 peers 뿐이었다.

## 왜 그렇게 동작하나

### `-sf` 는 연결을 살리고 테이블은 살리지 않는다

`[실측]` 리로드 직후 haproxy 두 개가 공존한다. 새 프로세스가 리스닝 소켓을 인수하고, 열어 둔 장수명 연결은
옛 프로세스가 계속 들고 있다가 연결이 닫히면 스스로 종료한다.

`[실측]` peers 없이 `-sf` 리로드하면 `show table` 의 used 가 1 → 0 이 된다. peers 를 넣으면 1 → 1 로 유지된다
(각 조건 1회, 다른 세션 기록). 다른 인계 경로는 조사하지 않았다.

`[문서]` peers 는 soft restart 때 옛 인스턴스가 local peer 로 새 인스턴스에 접속해 테이블을 전부 복제(teaching)하는
장치다. ⚠️ 당시 인용한 문서 파일은 실행 바이너리와 다른 버전(OS 패키지)의 것이었다 — 위 실측이 1차 근거다.

### 공존 구간에서 지속성이 갈라진다

`[추정]` 옛 프로세스는 자기 테이블대로 기존 연결을 멤버 A 에 붙여 두고, 같은 클라이언트의 새 연결은 새 프로세스가
빈 테이블로 받아 밸런싱 알고리즘이 고른 멤버(B 일 수 있음)에 기록한다. 이 창의 길이는 옛 프로세스의 기존 연결이
끝나는 시점까지 — 유휴면 `timeout client`, 계속 흐르는 연결이면 `hard-stop-after` 가 없을 때 상한이 없다.
같은 IP 가 두 프로세스에서 동시에 다른 멤버로 붙는 것을 직접 관측하지는 않았다.

### 옛 프로세스를 죽이는 쪽을 택한 구현

`[코드]` 포크된 OpenStack LB 에이전트(haproxy namespace 드라이버)는 LB update 에서 리스너의 default pool 세션 지속성이
SOURCE_IP 이면 새 프로세스를 `-sf` 로 띄운 뒤 옛 pid 를 전부 `kill -9` 한다. 2018-05 커밋 메시지:
"kill old haproxy processes to keep session persistency after restarting the process".
처음엔 lb_algorithm SOURCE_IP + 멤버 변경 조건이었고 일주일 뒤 세션 지속성 타입 조건으로 바뀌었다.

`[코드]` 조건은 `default_pool` 한정이다. L7 정책으로만 연결된 풀의 SOURCE_IP 는 이 분기에 걸리지 않는다.

### kill -9 가 보장하는 것과 하지 않는 것

- 보장: kill 이후로는 한 클라이언트의 모든 연결이 **한 프로세스, 한 테이블**을 거친다. `-sf` 가 새 프로세스를
  먼저 띄우므로 spawn 과 kill 사이의 짧은 창은 남는다.
- 보장하지 않음: 리로드 전 멤버 유지. 옛 테이블은 옛 프로세스와 함께 사라지고, 재접속 첫 요청은 빈 테이블을
  만나 알고리즘이 고른다.
- `[코드]` 풀 알고리즘이 `balance source` 해시고 멤버 구성이 같으면 같은 멤버가 다시 나올 수 있다.
  테이블이 살아남은 게 아니라 **재계산이 같은 답을 낸 것**이다.

### 쿠키 지속성은 이 문제가 없다

`[코드]` HTTP_COOKIE 는 `cookie SRV insert indirect nocache` + `server ... cookie <id>` 로 매핑이 설정 파일과
클라이언트 쿠키에 있다. 설정상 프로세스에 런타임 상태가 없어 옛/새 프로세스가 같은 쿠키를 같은 멤버로 보낼
것이고, 실제로 kill 분기 조건도 SOURCE_IP 만이다. 리로드 전후 쿠키 매핑 유지는 직접 관측하지 않았다
→ [[haproxy/cookie-session-persistence]].

## 확인하는 방법

2026-08-21 실측 기록(haproxy 3.0.15, netns 안 단일 프로세스). 출력은 당시 기록에서 옮겼다.

```
# 장수명 연결을 열어 둔 채 -sf 리로드 → 옛 프로세스가 연결을 보유
$ ip netns exec <ns> ss -tnp state established '( sport = :80 )'
... users:(("haproxy-3.0.15",pid=<old>,fd=13))

# stick-table 인계 여부 — peers 유무만 바꿔 같은 리로드, stats 소켓에 `show table <backend>`
# peers 없음:  리로드 전 used:1 → 리로드 후 used:0
# peers 있음:  리로드 전 used:1 → 리로드 후 used:1
```

리로드를 직접 유발할 때는 `haproxy -f <cfg> -sf $(cat <pid>)` 를 쓴다. 에이전트 경로(멤버 add/delete)로
유발하면 설정이 재생성되어 수동으로 넣은 peers 가 지워진다.

## 이 노트가 틀렸다면

- peers 없이 `-sf` 리로드 후 `show table` 의 used 가 유지된다 → "테이블은 넘어가지 않는다" 와 "확인된 인계 경로는
  peers 뿐" 이 함께 틀렸다(버전·설정에 따라 다른 인계 경로가 있다).
- 리로드 전후 같은 쿠키값의 요청이 다른 멤버로 간다 → 쿠키 지속성은 무영향이라는 주장이 틀렸다.
- kill -9 후 재접속한 클라이언트가 roundrobin 풀에서도 항상 리로드 전 멤버로 간다 → "연속성은 보장되지 않는다" 가 틀렸다.
- `[추정]` 공존 구간에 같은 IP 의 새 연결이 항상 옛 프로세스와 같은 멤버로 간다 → 갈라짐 추정이 틀렸다
  (적용 범위를 알고리즘별로 좁힌다).
- peers 를 넣은 채 kill -9 분기를 제거해도 공존 구간에 멤버가 갈라진다 → "테이블을 넘기는 유일한 길은 peers"
  또는 인계 완료 시점 가정이 틀렸다.

## 적용 범위

- `stick-table type ip` + `stick on src`, peers 미설정, 프로세스 1개. 실측은 haproxy 3.0.15.
- 테이블 인계 실측은 수동 peers 편집 + 직접 `-sf` 재기동 조건에서 한 것. 에이전트가 생성한 설정에는 peers 가 없다.
- kill -9 분기는 코드로만 확인했다. 그 분기로 연결이 끊기는 것을 직접 관측하지는 않았다.

## 함정

- "drain" 은 옛 프로세스가 **연결을 마무리하는 것**이지 테이블이 옮겨가는 것이 아니다. 두 말이 자주 섞인다.
- `balance source` 가 같은 멤버를 내는 것을 "테이블이 유지됐다"로 읽기 쉽다. 멤버 하나를 빼고 다시 보면 갈린다.
- ⚠️ `hard-stop-after` 가 없으면 잦은 리로드에 옛 프로세스가 누적된다.
- 💡 peers 를 넣으면 kill -9 분기는 불필요해질 것으로 보이나, 분기 제거는 코드 수정이라 미검증.
  인계가 끝나기 전에 옛 프로세스를 죽이면 오히려 인계가 실패할 수 있다(미확인).
