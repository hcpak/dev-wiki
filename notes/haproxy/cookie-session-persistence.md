# 쿠키 기반 세션 지속성 — 왜 LB 장비가 바뀌어도 유지되나

> 쿠키는 클라이언트가 만드는 게 아니라 **서버(여기선 LB)가 발급**하고 브라우저는 되돌려줄 뿐이다.
> `cookie ... insert` / `prefix` 는 "어느 백엔드로 갈지"를 **클라이언트 쿠키에 실어 보내는** 방식이라
> LB 쪽에 런타임 상태가 남지 않는다. 그래서 Active/Standby 가 뒤바뀌어도 그대로 동작한다.
> 반대로 `stick on src`(stick-table) 는 LB 메모리에만 있어서 장비가 바뀌면 유실된다.

## 왜 그렇게 동작하나

### 쿠키를 만드는 주체는 서버다

```
서버 → 클라이언트 :  Set-Cookie: SRV=<id-a>    (응답 헤더 — 발급)
클라이언트 → 서버 :  Cookie: SRV=<id-a>        (요청 헤더 — 되돌려줌)
```

브라우저는 **저장하고 되돌려주기만** 한다. LB 는 클라이언트와 백엔드 사이에 인라인으로 있으니
응답의 `Set-Cookie` 를 직접 심거나 고칠 수 있다. 지속성은 이 성질만으로 구현된다.

### 매핑표는 설정 파일 그 자체다

```
backend <be>
    mode http
    balance roundrobin
    cookie SRV insert indirect nocache
    server <id-a> <ip-a>:<port> weight 1 cookie <id-a>
    server <id-b> <ip-b>:<port> weight 1 cookie <id-b>
```

`server` 라인 뒤의 `cookie <값>` 이 **"이 쿠키값이면 이 서버"** 라는 대응이다.
트래픽이 흐르며 런타임에 쌓는 테이블이 아니라 **디스크의 설정 파일에 정적으로 박힌 값**이다.
이 한 줄이 이 문서 전체의 핵심이다.

### 요청 흐름

**1회차 (쿠키 없음)**

1. 요청에 `SRV` 쿠키가 없다
2. `balance` 알고리즘으로 서버를 고른다
3. 백엔드가 응답한다
4. LB 가 응답에 `Set-Cookie: SRV=<id-a>` 를 **끼워 넣어** 내려보낸다 (`insert`)

**2회차 이후**

5. 브라우저가 `Cookie: SRV=<id-a>` 를 실어 보낸다
6. LB 가 이 값을 `server` 라인의 `cookie` 값과 대조해 그 서버로 **직행**한다. **`balance` 는 무시된다**
7. `indirect` 라서 이 쿠키는 백엔드로 넘기기 전에 제거된다 → 애플리케이션은 존재조차 모른다

### 옵션 세 개

| 옵션 | 하는 일 |
| --- | --- |
| `insert` | 유효한 쿠키를 안 들고 온 클라이언트의 응답에 쿠키를 심는다 |
| `indirect` | 백엔드로 전달하기 전 그 쿠키를 제거한다. 이미 올바른 서버로 간 요청에는 재발급하지 않는다 |
| `nocache` | 쿠키를 심은 응답에 `Cache-control: private` 를 붙인다. 중간 캐시가 남의 쿠키를 캐싱하는 사고를 막는다 |

### insert 와 prefix

| 모드 | 동작 | 쓰는 상황 |
| --- | --- | --- |
| `cookie SRV insert ...` | LB 전용 쿠키를 **새로 만든다** | 앱이 쿠키를 안 쓰거나, 쿠키가 하나 늘어도 될 때 |
| `cookie <app-cookie> prefix ...` | 앱이 이미 쓰는 쿠키값 **앞에 서버 식별자 + `~` 를 붙인다** (`<app-cookie>=<id-a>~abc123`). 요청이 오면 접두사를 떼고 원본만 백엔드로 넘긴다 | 쿠키를 새로 늘릴 수 없을 때 |

원리는 같다 — 둘 다 상태를 클라이언트에게 맡기고, LB 는 설정 파일만 본다.

### stick-table 과 대조

출발지 IP 고착(`stick on src`)은 성격이 정반대다.

| | 쿠키 방식 | `stick-table` 방식 |
| --- | --- | --- |
| 매핑이 어디 있나 | 클라이언트 쿠키 + 설정 파일 | **LB 프로세스 메모리** |
| 트래픽이 흐르며 생기나 | 아니다 (설정에 이미 있다) | 그렇다 (IP 볼 때마다 기록) |
| 다른 장비가 이어받나 | 된다 | `peers` 없으면 안 된다 |
| 리로드 후 | 유지 | `peers` 없으면 유실 |
| L7 필요 | `mode http` 필수 | `mode tcp` 도 된다 |

Active/Standby 두 노드에 **같은 소스로 생성된 같은 설정 파일**이 배포되는 구성이라면,
쿠키 방식은 동기화 장치가 아예 필요 없다. Standby 도 `cookie <id-a>` 라는 똑같은 줄을 이미 갖고 있어서
클라이언트가 들고 온 쿠키를 해석하는 데 필요한 정보가 **전부 자기 설정 안에** 있다.

`stick-table` 을 장비 간에 이으려면 최상위에 `peers` 섹션을 선언하고 테이블에 붙여야 한다.
"옵션 한 줄"이 아니라 양 노드의 이름·주소를 아는 별도 구조다.

```
peers <pair-name>
    peer <node-a> <ip-a>:1024
    peer <node-b> <ip-b>:1024

backend <be>
    stick-table type ip size 10k peers <pair-name>
```

### 전제 — LB 가 평문 HTTP 를 봐야 한다

`cookie` 는 `mode http` 전용이다. TLS 를 LB 에서 풀지 않고 그대로 흘려보내는 패스스루 구성은
`mode tcp` 라 헤더가 암호문이고, 쿠키를 읽을 수도 심을 수도 없다.

| 앞단 처리 | mode | 쿠키 지속성 |
| --- | --- | --- |
| 평문 HTTP | http | 가능 |
| TLS 종료 | http | 가능 |
| TLS 종료 후 백엔드로 재암호화 | http | 가능 |
| TLS 패스스루 | tcp | **불가** |
| 순수 TCP | tcp | **불가** |

판별 기준은 프로토콜 이름이 아니라 **LB 가 평문을 보느냐**다.
재암호화는 앞단에서 한 번 풀기 때문에 이름에 TLS 가 들어가도 쿠키가 된다 — 패스스루와 헷갈리기 쉽다.

### 고착이 깨지는 경우 — `option redispatch`

지속성을 걸어도 **가용성이 우선**이라 고착이 의도적으로 끊기는 경로가 있다. 이걸 모르면
"쿠키를 넣었는데 왜 다른 서버로 갔냐"를 버그로 오해한다.

LB 는 백엔드 연결에 실패하면 `retries` 횟수만큼 재시도하는데, **기본은 실패한 그 서버로만** 다시 시도한다.
여기에 쿠키 고착이 겹치면 최악이 된다.

```
클라이언트가 SRV=<id-a> 쿠키 보유 → <id-a> 서버 다운
  → 쿠키가 <id-a> 지목 → 재시도도 <id-a> → 계속 실패
  → 클라이언트는 쿠키를 스스로 못 지운다 → 그 사용자만 영구 서비스 불가
```

`option redispatch` 는 이때 **고착을 의도적으로 깨고** 살아 있는 서버로 재분배한다.
HAProxy 문서도 이 옵션의 첫 번째 용도를 "쿠키 기반 고착을 끊기 위한 것"으로 설명한다.

```
defaults
    retries 3
    option redispatch
```

선택 인자 `<interval>` 의 **기본값은 `-1`** — 음수 N은 "마지막에서 N번째 재시도에 재분배"라
`-1` 이면 **마지막 재시도에서만** 다른 서버로 돌린다.

```
1차 시도  → A 실패
재시도 1  → A            (같은 서버)
재시도 2  → A            (같은 서버)
재시도 3  → B  ← 마지막 재시도에서 redispatch
```

양수 P면 P번째 재시도마다 재분배한다(`1` = 매 재시도마다).
⚠️ **`retries 0` 이면 이 옵션은 무의미하다** — 재시도가 없으면 재분배할 기회도 없다.

적용 범위가 좁다는 게 핵심이다.

| 상황 | 재분배되나 |
| --- | --- |
| 백엔드로 TCP 연결 자체가 안 됨 | 된다 |
| 쿠키가 지목한 서버가 DOWN 판정 | 된다 |
| 연결은 됐는데 응답 도중 끊김 | **안 된다** (이미 클라이언트로 응답이 나가기 시작함) |
| 백엔드가 5xx 를 응답으로 반환 | **안 된다** (연결은 성공한 것이라 재시도 대상이 아님) |

즉 "장애나면 알아서 딴 데로 넘겨주는 만능 장치"가 아니라 **연결 수립 단계 한정**이다.

재분배로 B 에 붙고 나면 `insert` 모드에서는 **B 용 쿠키를 새로 발급**받아 이후로는 B 에 고착된다.
A 가 살아 돌아와도 자동 복귀는 없다.

💡 반대 방향 옵션으로 `option persist`(DOWN 서버로도 계속 보냄)가 있지만, 가용성을 버리는 선택이라
세션을 서버 로컬에만 들고 있는 레거시가 아니면 쓸 일이 없다.

## 확인하는 방법

**① 쿠키를 심는지 본다** — 쿠키 없이 요청해 응답 헤더를 확인:

```bash
curl -sS -o /dev/null -D- "http://<vip>:<port>/"
```

```
HTTP/1.1 200 OK
Set-Cookie: SRV=<id-a>; path=/
Cache-control: private
```

`Set-Cookie` 가 안 보이면 그 백엔드에 지속성이 안 걸려 있거나 `mode tcp` 다.

**② 고착되는지 본다** — 받은 쿠키를 넣고 반복 요청해 늘 같은 백엔드로 가는지:

```bash
for i in $(seq 10); do
  curl -sS -o /dev/null -D- -b "SRV=<id-a>" "http://<vip>:<port>/" | grep -i '^x-served-by'
done
```

백엔드가 자기를 밝히는 헤더가 없으면 접근 로그의 서버 이름 필드로 본다.

**③ 쿠키를 빼고 분산되는지 본다** — `-b` 없이 같은 횟수를 돌려 여러 서버로 퍼지면
지속성이 실제로 일하고 있는 것이다. ②만 보면 "원래 한 대뿐인 상태"와 구분되지 않는다.

**④ stick-table 은 런타임 상태라 조회해야 보인다** (쿠키 방식은 볼 게 없다):

```bash
echo "show table <be>" | socat stdio /var/run/<sock>
```

```
# table: <be>, type: ip, size:10240, used:2
0x...: key=203.0.113.10 use=0 exp=... server_id=1
```

여기 쌓인 게 **장비가 바뀌면 사라지는 그 상태**다. 쿠키 방식 백엔드에는 이 테이블 자체가 없다 —
"조회했더니 비어 있다"가 아니라 "테이블이 없다"가 정상이다.

**⑤ 문법·경고 확인**: `haproxy -c -f <cfg>` → `Configuration file is valid`.
아래 첫 번째 함정 때문에 **valid 가 곧 동작 보장은 아니다.** 반드시 ①과 함께 본다.

## 함정

- ⚠️ **`mode tcp` 백엔드에 `cookie` 를 적으면 조용히 무시된다.** 설정 오류로 죽지 않고
  시작 시 경고만 남기고 넘어가는 것으로 알려져 있다(💡 로컬에서 미검증).
  "설정에 넣었으니 되겠지"가 가장 위험하다 — ①로 실제 `Set-Cookie` 를 확인할 것.
- ⚠️ **지속성은 best-effort 다.** `option redispatch` 가 켜져 있으면 연결 실패 시 고착을 깨고
  다른 서버로 넘어간다. "쿠키를 넣었으니 절대 안 바뀐다"는 보장이 아니다
  → [고착이 깨지는 경우](#고착이-깨지는-경우--option-redispatch)
- ⚠️ **그렇다고 redispatch 가 만능도 아니다.** 응답이 나가기 시작한 뒤의 실패나 백엔드가 반환한 5xx 는
  재분배 대상이 아니다. "redispatch 켜뒀으니 장애는 알아서 넘어간다"가 두 번째 오해다.
- ⚠️ **커넥션이 끊기는 것과 고착이 풀리는 것은 다른 층위다.** 장비 전환 시 이미 확립돼 있던 TCP 커넥션은
  쿠키와 무관하게 끊긴다(진행 중이던 요청·업로드·WebSocket 은 실패). 쿠키가 지켜주는 건
  **재연결 이후 어느 서버로 붙느냐**다. 이 둘을 뭉뚱그리면 "세션 유지되나요?"에 정반대로 답하게 된다.
- ⚠️ **쿠키 값에 서버 식별자가 그대로 노출된다.** 클라이언트가 값을 바꿔 특정 서버를 지목할 수 있다.
  식별자에 내부 호스트명·순번을 쓰면 구성 정보가 새어 나간다. 무의미한 UUID 가 안전하다.
- ⚠️ **`nocache` 를 빼면 중간 캐시가 `Set-Cookie` 붙은 응답을 캐싱해** 여러 사용자가 같은 쿠키를
  받을 수 있다. 그러면 전원이 한 서버로 몰린다.
- 💡 서버 식별자가 바뀌는 변경(백엔드 교체·재생성)을 하면 클라이언트의 옛 쿠키는 매칭에 실패해 재분배된다.
  무중단으로 보이지만 그 순간 고착은 초기화된다.
