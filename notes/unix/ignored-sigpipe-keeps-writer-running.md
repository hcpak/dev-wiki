# SIGPIPE 를 무시한 프로그램은 파이프를 받는 쪽이 끝나도 멈추지 않는다 — write 가 EPIPE 로 실패할 뿐이다

> `tool | head -3` 에서 head 가 끝나면 tool 의 다음 write 는 SIGPIPE 를 받는다.
> 기본 동작이면 tool 은 그 자리에서 죽고, 종료 시 정리 코드(설정 원복, lock 해제)를 건너뛴다.
> SIGPIPE 를 무시하면 죽지는 않지만 write 가 EPIPE 로 실패할 뿐이라, 반환값을 안 보는 루프는 계속 돈다.
> 파이프라인이 끝나지 않는다. 정리와 종료를 둘 다 얻으려면 무시가 아니라 **핸들러로 받아 종료 플래그를 세워야** 한다.

## 왜 그렇게 동작하나

`[문서]` 읽는 쪽이 모두 닫힌 파이프에 write 하면 커널이 쓰는 프로세스에 SIGPIPE 를 보낸다. SIGPIPE 의 기본 동작은 종료다. SIGPIPE 를 무시하거나 막아 두면 write 는 대신 `EPIPE` 로 실패한다 (pipe(7), write(2)).

`[실측]` 기본 동작에서는 tool 이 SIGPIPE 로 즉시 죽는다. 그래서 루프를 빠져나온 뒤 실행되는 정리 코드가 돌지 않는다. 이벤트를 출력하는 동안 커널 쪽 디버그 설정을 켜 두는 CLI 에서는, 설정과 필터가 켜진 채 남았다.

`[실측]` `signal(SIGPIPE, SIG_IGN)` 으로 바꾸면 tool 은 죽지 않는다. `printf` 의 반환값을 보지 않는 이벤트 루프는 출력이 실패해도 계속 poll 하므로, head 가 끝난 뒤에도 파이프라인이 반환되지 않았다. tool 이 쥔 lock 도 그대로 남아, 다른 실행이 "이미 실행 중" 으로 거부됐다. 사람이 Ctrl+C(SIGINT)를 보내야 정상 정리하고 끝났다.

`[실측]` SIGINT 와 같은 핸들러(`exiting = true` 만 세우는 함수)로 SIGPIPE 를 받으면, 루프가 다음 반복에서 빠져나와 정리하고 끝난다. head 가 끝난 지 1초 남짓에 파이프라인이 반환됐다.

`[문서]` 핸들러로 받은 시그널은 `execve` 때 기본 동작으로 돌아가고, 무시(SIG_IGN)한 시그널은 무시된 채로 넘어간다 (execve(2)). 그래서 핸들러 방식은 `popen` 등으로 띄우는 자식에게 영향을 주지 않지만, SIG_IGN 방식은 자식도 SIGPIPE 를 무시한 채 태어난다.

`[실측]` stdout 이 파이프면 stdio 는 줄 단위가 아니라 블록 단위로 버퍼링한다. 출력이 적으면 head 가 첫 줄을 받는 것 자체가 늦어진다. 초당 이벤트가 5건 정도일 때는 15초가 지나도 head 가 끝나지 않았고, 초당 200건으로 올리자 1.3초에 끝났다. `[추정]` 블록 크기는 약 4KB 로 보이지만 이번에 확인하지는 않았다.

## 확인하는 방법

veth 에 이벤트 발생원을 붙여 초당 약 200건이 나오게 하고, 세 가지 빌드를 5초 뒤 상태로 비교했다.

```
$ ( tool -f <filter> | head -3 >/dev/null; touch done ) & sleep 5
기본 동작   : 파이프라인 반환(1.3초), tool 종료, 디버그 설정·필터 남음
SIG_IGN    : 파이프라인 미반환, tool 생존, 설정 유지, 두 번째 실행은 lock 으로 거부 → SIGINT 후 정리·종료
핸들러      : 파이프라인 반환(1.3초), tool 종료, 설정·필터 정리됨
```

## 이 노트가 틀렸다면

- SIG_IGN 빌드가 head 종료 후 스스로 끝난다 → 그 프로그램은 write 실패를 검사해 루프를 빠져나오는 것이다. 이 노트의 "계속 돈다" 는 반환값을 안 보는 루프에만 해당한다
- 기본 동작 빌드가 SIGPIPE 후에도 정리 코드를 실행한다 → atexit 나 다른 경로로 정리하는 것이니, "정리를 건너뛴다" 는 그 프로그램에 적용되지 않는다
- 핸들러 빌드에서 `popen` 한 자식이 SIGPIPE 를 무시한다 → execve 의 재설정 규칙이 기대와 다른 것이다

## 적용 범위

`[실측]` Linux, glibc, C 로 짠 BPF ring buffer polling CLI 에서 확인했다. 컨테이너(Ubuntu 24.04)와 물리 노드(Ubuntu 22.04, 커널 5.15) 두 곳에서 같은 결과였다.
`[추정]` 원리상 stdout 에 쓰며 무한 루프를 도는 모든 C 프로그램에 해당한다. Python 은 SIGPIPE 를 기본으로 무시하고 `BrokenPipeError` 예외를 내므로 양상이 다르다 — 확인하지 않았다.

## 함정

- ⚠️ "SIGPIPE 때문에 정리를 못 한다" 를 SIG_IGN 으로 고치면, 대화형 사용에서는 Ctrl+C 를 한 번 더 누르는 정도라 문제가 안 보인다. 스크립트나 cron 처럼 Ctrl+C 를 누를 사람이 없는 곳에서는 설정을 켠 채 무기한 남는다.
- ⚠️ 출력이 적은 환경에서 `| head` 재현을 시도하면 블록 버퍼링 때문에 어떤 빌드든 끝나지 않는다. 버그와 버퍼링을 구분하려면 출력량을 먼저 올린다.
- 💡 시그널 하나만 따로 다루지 말고 SIGINT, SIGTERM, SIGHUP, SIGPIPE 를 같은 핸들러로 받으면 종료 경로가 하나로 모인다. SIGHUP 은 nohup 실행을 고려해야 한다 — [[nohup-children-start-with-sighup-ignored]].
