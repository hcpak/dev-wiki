# 워크로드가 이관된 호스트는 옛 버전을 진실처럼 말한다

> 서비스를 다른 실행 환경(컨테이너 등)으로 옮겨도 옛 호스트에는 **패키지·로그·유닛이 그대로 남는다.** 그걸 근거로 "지금 배포된 버전"이나 "로그가 안 남는다"를 판정하면 오진한다. 그리고 잔존이 조회를 오염시키는 데서 끝나지 않는 경우가 있다 — **잔존 유닛이 실행 중이면 공유 메시지 큐의 컨슈머로 실제 트래픽까지 오염시킨다.**

**상태**: 활성
**마지막 검증**: 2026-08-21

## 왜 그렇게 동작하나

이관은 보통 "새 환경에 띄우고 옛 유닛을 정지"로 끝난다. 옛 호스트에서 **제거되는 것은 거의 없다.**

- [실측] 패키지는 언인스톨하지 않는다 → 패키지 조회는 **이관 시점의 버전**을 계속 보고한다
- [실측] 로그 파일은 남아 있고, 로테이션이 한 번 더 돌면 **빈 파일**이 새로 생긴다 → "로그가 비어 있다"
- [코드] 설정 파일도 그대로다 → 설정을 고쳐도 아무 일도 일어나지 않는다

즉 옛 호스트는 조회에 다 응답하지만, 그 답은 전부 과거형이다. 조회가 성공한다는 점이 함정이다 — 실패하면 오히려 의심하게 되는데, 성공하니 그대로 믿는다.

**정지 자체가 누락된 변형이 더 위험하다.**

- [실측] 마스킹 절차가 있어도 호스트별로 부분 누락된다 — 같은 역할의 형제 호스트는 `masked` 인데 한 대만 `enabled` 로 남아, 재부팅·수동 기동으로 옛 프로세스가 되살아난 사례가 있다.
- [실측] 그 위에 새 패키지가 설치되어도 **서비스 재시작이 없으면 프로세스는 구버전 코드로 계속 돈다** — 디스크의 패키지 버전과 메모리의 실행 코드가 갈라진다.
- [추정] 이 구버전 프로세스가 신버전 컨슈머들과 **같은 RPC 큐를 나눠 소비**하면, 메시지가 구버전에 분배된 경우에만 오동작(신규 필드 누락 등)이 나타난다 → 지속 장애가 아니라 **발생↔해소를 반복하는 간헐(플래핑) 장애**가 되어 원인 추적이 어렵다. (근거: 배포 시작 직후부터 간헐 장애 시작, 프로세스 중지 이후 재발 없음, API 는 LB 뒤라 영향 없던 정황)

## 확인하는 방법

**서비스가 그 호스트에서 실제로 돌고 있는지**를 먼저 본다. 버전은 그 다음이다.

```bash
systemctl is-active <svc>                               # inactive 면 이 호스트는 판정 근거가 아니다
systemctl show <svc> -p ExecMainStartTimestamp          # 마지막 기동 시각 = 이관/기동 시점의 흔적
systemctl is-enabled <svc>                              # 이관 완료라면 disabled/masked 여야 한다
```

- 마지막 기동 시각이 **로그가 비기 시작한 날짜와 일치**하면, 로그 유실이 아니라 이관이다.
- 마지막 기동 시각이 **프로세스가 실행한 코드의 버전**을 정한다 — 그 이후 설치된 패키지는 재시작 전까지 반영되지 않는다.
- 실제 버전은 **워크로드를 관리하는 쪽의 스펙**에서 읽는다. 오케스트레이터라면 워크로드 정의의 이미지 태그가 단일 진실 공급원이다.

```bash
<orchestrator> get <workload> -o custom-columns='NAME:.metadata.name,IMAGE:...image'
```

## 이 노트가 틀렸다면

- 이관 절차가 옛 호스트의 패키지 제거·유닛 mask 까지 포함하고 전 호스트에서 완료된 것이 확인되면 → "잔존한다"는 전제가 그 환경에서는 성립하지 않는다 (적용 범위 축소)
- 잔존 유닛이 `active` 인데 메시지 브로커 포트로의 연결이 0 (`ss -tnp | grep <broker-port>`) 으로 관측되면 → "실행 중 잔존이 트래픽을 오염시킨다"는 주장이 그 서비스에는 적용되지 않는다 (큐 접속 정보가 회수된 경우 등)
- 워크로드 스펙의 이미지 태그와 실제 실행 코드가 다른 사례가 관측되면 → "스펙이 단일 진실 공급원" 주장이 무너진다 ([[version-skew-in-image-pins]] 의 스큐가 그 반례 후보)

## 적용 범위

- VM/베어메탈 유닛 → 컨테이너 오케스트레이터로의 이관. systemd 기반 호스트.
- 트래픽 오염 주장은 **브로커 큐를 경쟁 소비하는 RPC 구조**(oslo.messaging 류)에 한정. HTTP API 처럼 LB 가 라우팅을 통제하는 경로는 잔존 프로세스로 가지 않는다.

## 함정

- ⚠️ **"로그가 안 남는다"를 로그 유실 결함으로 오진**하기 쉽다. 별건 티켓까지 만들었다가, 유닛이 몇 주 전부터 `inactive` 였다는 걸 뒤늦게 발견하는 식이다. 로그가 빈 것은 증상이지 원인이 아니다.
- ⚠️ **간헐 플래핑 장애에서 잔존 프로세스는 용의선상에 잘 안 오른다** — 새로 배포한 것만 뒤지게 된다. "배포로 무엇이 추가됐나"만이 아니라 "무엇이 **덜** 갱신됐나"를 같이 봐야 한다.
- ⚠️ 이관된 서비스의 로그를 보려면 **새 실행 환경 쪽 접근 권한**이 필요하다. 그 권한이 없으면 "조사 가능"이라고 가정하고 계획을 세우면 안 된다 — 실제로 리전별로 권한이 갈려 한쪽만 조회되는 경우가 있다.
- ⚠️ 이관 여부는 리전·환경마다 다르게 진행된다. 한 곳에서 확인한 구조를 다른 곳에 그대로 적용하면 틀린다.
- 💡 옛 호스트에 패키지를 설치·재시작해도 서비스에는 영향이 없다 — 단, 이는 유닛이 정지됐을 때 얘기다. 아무 일도 안 일어나는 배포는 "성공한 배포"처럼 보여서 더 위험하고, 유닛이 살아 있으면 반대로 "재시작 안 한 배포"가 구버전 프로세스를 방치한다.

## 처방

- 버전 판정의 **단일 출처를 워크로드 스펙으로 고정**하고, 호스트의 패키지 조회는 보조 근거로만 쓴다.
- 진단 절차의 첫 줄을 "이 서비스가 어디서 도는가"로 둔다. 로그 경로·패키지 버전은 그 답이 나온 뒤에 의미가 생긴다.
- 이관이 끝난 호스트는 유닛을 stop 이 아니라 **disable + mask** 까지 해 둔다. stop 만 하면 enabled 유닛이 재부팅에 되살아난다.
- 이관이 끝난 호스트는 조회 대상 목록에서 빼거나, 문서에 "이관됨 — 판정 근거 아님"을 명시한다.
