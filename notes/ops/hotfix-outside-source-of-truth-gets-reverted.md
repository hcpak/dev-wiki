# 정본에 반영 안 된 핫픽스는 다음 배포가 조용히 되돌린다

> 노드에서 설정을 직접 고치고 구성관리 정본(salt state 등)에 반영하지 않으면, 다음
> 전체 배포가 정본의 옛 값으로 노드를 되돌린다. 수개월 뒤 같은 증상이 재발하는데,
> 그 사이 어디에도 에러가 없어서 "새 배포가 낸 버그"처럼 보인다.

**상태**: 활성
**마지막 검증**: 2026-08-24

## 왜 그렇게 동작하나

- 구성관리 도구(salt 등)는 노드를 **정본에 적힌 상태로 수렴**시키는 물건이다. 노드 로컬의
  수동 변경은 "보존할 커스텀"이 아니라 "교정할 드리프트"로 취급된다. `[문서]`
- 그래서 사건은 이렇게 진행된다: 장애 → 노드에서 직접 값 수정(증상 해소) → 정본 미반영 →
  수개월 뒤 다른 목적의 배포가 그 파일을 정본 값으로 재작성 → **옛 버그가 그대로 부활**. `[실측]`
  (과거 동일 증상 이슈에서 노드만 수정된 이력이 확인됐고, 정본 레포에는 해당 값의 변경
  커밋이 없었으며, 이후 배포 직후부터 증상이 재발)
- 부활 시점에 아무 에러도 없다 — 배포는 성공이고, 되돌아간 값도 "유효한" 값이기 때문.
  증상만 재발한다.

## 확인하는 방법

재발 의심 시 노드 파일의 mtime 과 배포 시각, 그리고 정본의 변경 이력을 대조한다:

```
$ ls -l /etc/<pkg>/<conf>          # mtime 이 배포 시각과 일치하는가
$ systemctl show <unit> -p ActiveEnterTimestamp
$ git log -p -- <정본 경로>        # 정본에 그 값의 변경 커밋이 있는가 (없으면 핫픽스가 정본 밖이었던 것)
```

이번 실측에서는: conf mtime = 배포 시각, 정본 레포는 해당 값이 1년 넘게 무변경, 과거
이슈 댓글에 "노드 수정 요청"만 있고 정본 반영 요청이 없었다.

## 이 노트가 틀렸다면

- 배포 도구가 노드 로컬 변경을 감지해 보존하거나 병합(3-way)하는 것이 관측되면 → 이 노트는
  그 도구·그 리소스에는 적용되지 않는다.
- 정본에 변경 커밋이 있는데도 옛 값이 배포됐다면 → 원인은 "정본 미반영"이 아니라 배포
  파이프라인의 다른 문제(잘못된 브랜치·캐시 등)이고, 이 노트로 진단을 멈추면 안 된다.

## 적용 범위

- 정본이 노드 밖(git 레포·salt state)에 있고 배포가 정본 기준으로 파일을 재작성하는 구조
  전반. 이번 실측은 salt 관리 conf 파일.

## 함정

- ⚠️ **배포 직후 터진 회귀는 "새 코드 버그"보다 "옛 값 복원"을 먼저 의심**할 것 — conf diff
  가 코드 diff 보다 먼저다.
- ⚠️ 조치가 노드 수정으로 끝났으면 그 조치는 끝난 게 아니다. "노드 수정 + 정본 반영 요청"을
  한 세트로 묶어야 한다 (운영 담당도 같은 요청을 했다).
- 💡 같은 증상의 **과거 이슈를 찾으면 조치 방식까지 읽을 것** — "그때 정본까지 고쳤는가"가
  이번 재발의 원인 후보를 바로 알려준다.
