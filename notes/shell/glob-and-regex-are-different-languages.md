# glob 과 regex 는 기호를 공유하지만 다른 언어다

> `*` `?` `.` 이 양쪽에 다 있지만 뜻이 다르다. glob 의 `*` 는 "임의의 문자열", regex 의 `*` 는
> "앞 문자의 반복" 이다. 실행 주체도 다르다 — glob 은 명령이 시작되기 **전에 셸이** 확장하고,
> regex 는 문자열로 프로그램에 넘겨져 **그 프로그램이** 매칭한다. 그래서 regex 를 따옴표로 안 감싸면
> 셸이 자기 것인 줄 알고 먼저 먹는다.

**상태**: 활성
**마지막 검증**: 2026-08-21

## 왜 그렇게 동작하나

### 확장 시점이 다르다

`[실측]` `ls *.txt` 에서 `ls` 는 `*.txt` 를 보지 못한다. 셸이 디렉터리를 읽어 `a.txt b.txt` 로
치환한 뒤 `ls` 를 실행한다. glob 은 명령이 뜨기 전에 이미 끝나 있다.

`[실측]` regex 는 반대다. `grep -E '.*\.txt'` 는 패턴을 **문자열 인자로** grep 에 넘기고, 매칭은
grep 내부에서 일어난다. 셸은 내용을 모른다.

여기서 실무 사고가 나온다. regex 를 따옴표로 감싸지 않으면 셸이 glob 으로 먼저 해석해서, 프로그램은
패턴 대신 **파일명을** 받는다.

### 매칭 범위가 다르다

`[실측]` glob 은 이름 **전체**를 맞혀야 한다. regex 는 기본이 **부분 일치**이고, 전체로 만들려면
`^ $` 로 묶어야 한다. 그래서 glob `*.txt` 는 regex `^.*\.txt$` 에 대응한다.

### 같은 기호, 다른 뜻

| 기호 | glob | regex | 대응 |
| --- | --- | --- | --- |
| `*` | 임의의 문자열 (0자 이상) | **앞 문자**의 0회 이상 반복 | glob `*` = regex `.*` |
| `?` | 임의의 한 문자 | 앞 문자가 0회 또는 1회 | glob `?` = regex `.` |
| `.` | **특수문자가 아님. 그냥 점** | 임의의 한 문자 | glob `.` = regex `\.` |
| `[abc]` | 문자 클래스 | 문자 클래스 | 같음 |
| 부정 | `[!a]` | `[^a]` | 기호가 다르다 |
| 선택 | POSIX glob 에 없음 (zsh 는 `(a|b)`) | `a|b` | — |

`[실측]` `.` 의 차이가 특히 잘 드러난다. glob 에서 `...txt` 는 특수문자가 하나도 없으므로 **패턴이
아니라 평범한 단어**다. 그래서 zsh 는 0건 에러도 내지 않고 `...txt` 를 그대로 넘긴다. 같은 문자열을
regex 로 주면 "임의의 글자 3개 + txt" 라서 `a.txt`(txt 앞이 2글자)조차 못 맞힌다.

`[실측]` 표현력도 glob 이 의도적으로 약하다. 그룹 반복·역참조가 없다. 할 일이 "파일명 고르기" 하나라
그 이상이 필요 없었다. (zsh 의 `EXTENDED_GLOB` 은 예외적으로 regex 급까지 확장된다)

## 확인하는 방법

zsh 5.9. 대상은 `a.txt  b.txt  script.sh  sub/`.

```
$ echo a*t                       # glob: a로 시작, t로 끝
a.txt

$ ls | grep -E "a*t"             # regex: a를 0회이상 + t → t가 있으면 다 걸림
a.txt b.txt script.sh

$ echo ...txt                    # glob: . 은 특수문자가 아니라 패턴이 아님
...txt

$ ls | grep -E "...txt"          # regex: 임의 3글자 + txt
(0건)
```

따옴표를 안 쳤을 때 프로그램이 실제로 받는 인자.

```
$ printf '받은 인자: %s\n' a*t      # 따옴표 없음 → 셸이 먼저 확장
받은 인자: a.txt

$ printf '받은 인자: %s\n' "a*t"    # 따옴표 있음 → 패턴이 그대로 전달
받은 인자: a*t
```

## 이 노트가 틀렸다면

- `echo a*t` 와 `ls | grep -E "a*t"` 가 같은 결과를 내면
  → `*` 의 의미가 양쪽에서 같다는 뜻이고, 이 노트의 핵심 대비가 틀렸다
- 따옴표 없이 넘긴 `a*t` 를 프로그램이 `a*t` 로 받으면
  → 셸이 먼저 확장한다는 설명이 틀렸다. `printf '%s\n'` 로 받은 인자를 직접 찍어 확인한다
- glob `*.txt` 가 `report.txt.bak` 을 맞히면
  → glob 이 이름 전체 매칭이라는 주장이 틀렸다 (부분 일치라는 뜻)
- `echo ...txt` 가 `no matches found` 로 죽으면
  → "특수문자가 없으면 패턴이 아니다" 가 틀렸거나, `.` 을 특수문자로 보는 설정이 켜져 있다

## 적용 범위

- `[실측]` zsh 5.9 / macOS(darwin 24), `grep -E`(BSD grep). 위 출력 전부 이 환경
- 기호 대응표는 POSIX 기본 glob 기준이다. zsh `EXTENDED_GLOB`·bash `extglob` 을 켜면 선택·반복
  문법이 추가되어 표의 "선택: 없음" 줄이 달라진다
- `[추정]` PCRE(`grep -P`)·Python `re` 도 같은 대비가 성립할 것으로 보지만, 이 노트에서는 확인하지
  않았다 — `*` `?` `.` 의 의미만 놓고 보면 동일 계열이다

## 함정

따옴표 누락이 가장 잦다. 증상이 "regex 가 안 맞는다" 로 나타나서 패턴을 계속 고치게 되는데, 실제로는
패턴이 프로그램에 도달하지 못한 것이다. 의심되면 `printf '%s\n' <패턴>` 으로 인자를 먼저 찍어본다.

⚠️ 이 사고는 **패턴이 우연히 파일명을 맞혔을 때만** 발생한다. 맞히는 파일이 없으면 zsh 는 에러를
내며 멈추고(오히려 안전), bash 는 패턴을 그대로 통과시켜서 정상 동작한다. 즉 **같은 명령이 디렉터리
내용에 따라 되기도 하고 안 되기도 한다.** 재현이 안 되는 버그로 보이는 이유다.

glob 을 regex 로 옮길 때 `.` 이스케이프를 빠뜨리기 쉽다. glob `*.txt` 를 regex `.*.txt` 로 적으면
`aXtxt` 도 맞는다. `.*\.txt` 가 맞다.
