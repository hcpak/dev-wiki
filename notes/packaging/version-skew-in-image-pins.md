# 이미지 패키지 핀과 버전 스큐 — 절반만 배포된 변경

> 하나의 기능을 여러 배포용 패키지에 나눠 만들면, 이미지에 그 전부를 함께 올려야 완성된다.
> 한쪽 핀만 올리면 빌드도 배포도 성공하는데, 런타임에 `AttributeError`로 터지거나 —
> 더 나쁘게는 — **아무 에러 없이 기능만 조용히 빠진다.**

**상태**: 활성
**마지막 검증**: 2026-08-18

## 왜 그렇게 동작하나

컨테이너 이미지가 여러 개의 배포용 패키지를 각각 버전으로 고정(pin)해 조립하는 구조를 생각하자.

```yaml
packages:
  - <pkg-caller>: 1.0.0~rc7-1     # 새 메서드를 "호출"하는 쪽
  - <pkg-impl>:   1.0.0~rc7-1     # 그 메서드를 "구현"하는 쪽
```

한 기능이 두 저장소에 걸쳐 구현되면 완성에는 **두 핀 모두** 올려야 한다. 그런데 호출측 핀만 올리면:

- `[실측]` 이미지 빌드는 성공한다 — 두 패키지 다 설치 가능한 실제 버전이므로
- `[실측]` 기동도 성공한다 — 파이썬은 **속성 접근 시점에** 이름을 찾으므로, import 시점엔 문제가 없다
- 해당 코드 경로를 처음 타는 순간 터진다

```
AttributeError: '<SomePlugin>' object has no attribute '<new_method>'
```

동적 언어라 **링크 단계에서 잡히지 않는다.** C였다면 링크 에러로 빌드가 깨졌을 것이 여기서는
런타임까지 미뤄진다. 정적 타입 검사나 통합 테스트가 그 경로를 밟지 않으면 배포까지 통과한다.

### 스큐는 에러조차 안 낼 수 있다 (조용한 스큐)

`[실측]` 빠진 코드가 "호출되는 메서드"가 아니라 **조건 분기의 한 가지**면 예외도 로그도 없다.
구버전 코드는 그 케이스를 `else: return`으로 흘려보낼 뿐이므로, 증상은 "특정 유형에서만
기능이 동작하지 않음"으로 나타나고 트레이스백이 없어서 버전 스큐를 의심하기 어렵다.
2026-08 실측: 디스패치 분기에 device_owner 한 종류를 추가한 수정이 이미지에 빠졌는데,
빠진 유형의 이벤트만 조용히 무시되고 나머지는 전부 정상이었다 — 대상 노드의 등록 맵을
덤프해 "있어야 할 엔트리가 없다"를 보고서야 역추적이 시작됐다.

### rc 번호가 같다고 짝이 맞는 게 아니다

가장 헷갈리는 지점이다. 저장소마다 rc 번호는 **독립적으로** 올라간다.

| | 호출측 | 구현측 |
| --- | --- | --- |
| 기능이 처음 들어간 버전 | `rc7` | `rc8` |
| 이미지에 핀된 버전 | `rc7` ✅ | `rc7` ❌ |

둘 다 `rc7`이라 눈으로는 정합해 보이지만, 구현측은 `rc8`이어야 한다. **같은 번호 = 같은 시점이 아니다.**

여기에 이미지 자신의 태그(`<image>:1.0.0-rc.9`)까지 겹치면 세 종류의 rc 번호가 돌아다닌다.
이미지 태그가 `rc.9`라고 해서 내용물 패키지가 `rc9`인 것은 전혀 아니다.

### 배포 경로가 둘이면 "반영 완료"도 경로별로 확인해야 한다

`[실측]` 같은 패키지가 **VM 노드(구성관리 도구 경유)** 와 **컨테이너(이미지 핀 경유)** 두 경로로
배포되는 환경에서는, 한쪽 경로에만 반영되고도 "반영 완료" 회신이 온다. 2026-08 실측:
새 rc를 안내하자 담당자가 구성관리 저장소에는 반영(머지)했지만 이미지 핀 파일은 그대로였고,
누구도 그 차이를 알아차리지 못했다 — 안내한 쪽도 "이미지도 갱신해 달라"는 문구를 빼먹었다.
반영 확인은 "머지됐나"가 아니라 **경로별 최종 산출물**(노드 dpkg / 컨테이너 dpkg)로 한다.

## 확인하는 방법

컨테이너 **안**에 실제로 설치된 버전을 본다. 이미지 태그는 근거가 되지 못한다.

```bash
kubectl exec -n <ns> <pod> -- dpkg -l | grep -E '<pkg-caller>|<pkg-impl>'
```
```
ii  <pkg-impl>      1.0.0~rc7-1   all   ...
ii  <pkg-caller>  2:1.0.0~rc7-1   all   ...
```

그리고 문제의 심볼(메서드든 분기 조건이든)이 실제로 파일에 있는지 직접 센다. 이게 가장 확실한 판정이다.

```bash
kubectl exec -n <ns> <pod> -- bash -c \
  "grep -c <new_symbol> /usr/lib/python2.7/dist-packages/<impl_pkg_path>/<file>.py"
# 0  ← 구현이 없음  (2026-08-18 실측: 분기 상수 grep 3회 → 수정판 4회로 판별)
```

저장소 쪽에서는 "이 커밋이 어느 태그부터 포함됐는지"를 본다.

```bash
git tag --contains <commit>
# 핀 파일 쪽은: 그 패키지 핀을 바꾼 커밋이 존재하는지
git log --oneline -S '<pkg-impl>' -- <packages.yaml>
```

## 이 노트가 틀렸다면

- 핀이 어긋난 이미지의 빌드가 **빌드 단계에서** 실패하는 것이 관측되면 → "빌드 성공 = 정합 아님" 주장이
  그 빌드 체계에는 적용되지 않는다 (예: 핀 정합성 검사 단계가 추가된 경우)
- 조건 분기 누락이 런타임 에러나 경고 로그를 남기는 것이 관측되면 → "조용한 스큐" 절의 적용 범위가 좁아진다
  (해당 코드베이스가 unknown 케이스를 명시적으로 로깅하는 경우)

## 적용 범위

- 파이썬(동적 바인딩) 패키지를 버전 핀으로 조립하는 컨테이너 이미지. 정적 링크 언어에는 앞 절반이 해당 없음
- 수동으로 관리되는 핀 목록 (자동 정합성 검사가 없는 경우)

## 함정

- **빌드 성공 = 정합 아님.** 핀이 실재하는 버전이기만 하면 빌드는 통과한다.
- ⚠️ **핀 파일을 고치는 사람과 기능을 만든 사람이 다를 때 잘 샌다.** 구현측 태그가 이미 나와 있어도,
  몇 시간 뒤 다른 사람이 호출측만 올리면서 그 태그를 집어가지 않으면 그대로 누락된다.
  "태그를 안 냈다"와 "태그는 났는데 핀을 안 올렸다"는 원인이 다르고 조치도 다르다.
- ⚠️ **"태그를 냈고 안내도 했다"조차 안전하지 않다** (2026-08 실측). 안내 댓글에 이미지 갱신 요청이
  빠지면 핀은 아무도 안 올린다. 다른 담당자들이 패키지 안내와 이미지 갱신을 항상 한 쌍으로 하고
  있었다면, 그 관행에서 벗어난 안내가 누락 지점이다.
- 💡 수동 핀 목록이 길수록(10개 이상) 이 사고가 반복된다. 이미지 태그를 찍기 전에
  **각 저장소 최신 rc 태그 ↔ 핀 값**을 대조하는 점검을 넣으면 걸러진다.
- 에러가 나는 변형에서 사용자에게 보이는 증상은 `500 Internal Server Error` 하나뿐이다. 어느 패키지가
  문제인지는 트레이스백 **마지막 두 줄**(호출한 파일:라인 + AttributeError)에 다 들어 있다.
- 이런 실패는 특정 리소스가 아니라 **그 코드 경로 전체**를 막는다. "특정 자원만 안 지워진다"는
  최초 제보가 실제로는 "전부 안 지워진다"인 경우가 많다.
