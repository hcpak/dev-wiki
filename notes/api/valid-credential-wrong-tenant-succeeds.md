# 잘못 배포된 자격증명이 유효하면 실패가 아니라 남의 데이터가 된다

> 멀티테넌트 수집 게이트웨이에 다른 테넌트의 자격증명이 배포되면, 인증도 전송도 전부
> 성공(2xx)하면서 데이터만 엉뚱한 테넌트 밑으로 들어간다. 송신 측에는 에러가 한 줄도
> 남지 않으므로 "전송 로그 정상"을 근거로 송신 구간을 결백 처리하면 원인을 놓친다.

**상태**: 활성
**마지막 검증**: 2026-08-24

## 왜 그렇게 동작하나

- 멀티테넌트 push 게이트웨이(OAuth2 client_credentials + remote write 류)는 요청을
  "자격증명이 유효한가"로만 판정하고, **데이터의 귀속은 자격증명→테넌트 매핑으로 결정**한다.
  자격증명이 어느 테넌트 것이든 유효하기만 하면 요청은 성공이다.
- 그래서 환경 A 노드에 환경 B 의 client_id/secret 이 배포되면: 토큰 발급 성공 → push 2xx →
  송신 에이전트(telegraf 등)의 write 에러·버퍼 적체·drop 카운터 전부 0. `[실측]`
- 수신 측에서는 환경 A 테넌트에 데이터가 전혀 없다. `[실측]` (수신 담당이 "해당 환경 전체가
  특정 시각부터 미수신"으로 관측 — 그 시각이 잘못된 자격증명이 배포된 시각과 일치)
- 데이터가 환경 B 테넌트에서 실제로 조회되는지는 확인하지 않았다. `[추정]` — "남의 데이터가
  된다"는 부분은 2xx 수용이라는 정황 추론이고, B 쪽에서 조회해 본 적은 없다.

## 확인하는 방법

송신 로그는 끝까지 무증상이다 (batch write 성공 + 에러 0):

```
$ tail /var/log/telegraf/telegraf.log
D! [outputs.http]  Wrote batch of 1000 metrics in 14.486281ms
D! [outputs.http]  Buffer fullness: 0 / 100000 metrics
$ grep -c 'E!' /var/log/telegraf/telegraf.log
0
```

진짜 확인은 로그가 아니라 **값 대조**다: 배포된 client_id 를 환경별 자격증명 정본(정리
문서·발급 이력)과 대조하고, 수신 담당에게 "이 client_id 가 이 환경 것이 맞는지"를 묻는다.

## 이 노트가 틀렸다면

- 게이트웨이가 테넌트 불일치 자격증명을 4xx 로 거부하는 것이 관측되면 → 그 게이트웨이는
  자격증명과 수신 채널이 결합돼 있는 것으로, 이 노트의 "성공으로 넘어간다"가 적용되지 않는다.
- 환경 B 테넌트를 조회했는데 데이터가 없으면 → "남의 데이터가 된다"는 틀렸고 "버려진다"로
  고쳐야 한다 (송신 무증상이라는 본론은 유지).
- 송신 에이전트에 자격증명 오류가 아닌 다른 형태(예: 4xx 아닌 경고)로라도 흔적이 남는 것이
  확인되면 → "송신 측 무증상" 주장이 좁아진다.

## 적용 범위

- OAuth2 client_credentials 로 인증하는 멀티테넌트 push 수집 게이트웨이 + telegraf
  `outputs.http`(prometheusremotewrite) 조합에서 실측. 같은 구조(자격증명이 곧 귀속 키)면
  다른 스택에도 성립할 것으로 본다. `[추정]`

## 함정

- ⚠️ 송신측 에러 카운터 기반 워치독은 이 유형을 **원리적으로 못 잡는다** — write 실패가 없기
  때문. 잡으려면 수신측(테넌트별 최근 수신 시각) 감시가 필요하다.
- ⚠️ 원인 조사에서 "push 성공 로그"를 종착 증거로 삼지 말 것. 성공은 "어딘가에 수용됐다"까지만
  말해준다. [[lost-response-is-not-a-failed-write]] 의 쌍대: 그쪽은 "응답 없음 ≠ 실패", 이쪽은
  "성공 응답 ≠ 의도한 효과".
- 💡 자격증명이 환경별로 다른 시스템은 환경명↔자격증명 대조표를 정본 문서로 유지하는 것이
  이 유형의 최단 진단 경로였다 (대조표 한 번으로 원인 확정).
