# 응답을 못 받은 것과 요청이 실패한 것은 다르다

> 쓰기 요청이 서버에 도달해 반영된 뒤 응답만 유실될 수 있다. 이때 실패로 보고 재시도하면
> 같은 쓰기가 두 번 일어난다. 재시도 전에 **상태를 읽어 확인**하는 단계가 필요하다.

**상태**: 활성
**마지막 검증**: 2026-08-21

## 왜 그렇게 동작하나

클라이언트가 관측할 수 있는 것은 "응답을 받았다 / 못 받았다" 뿐이다. 못 받은 경우는 최소 세 가지다.

```
① 요청이 서버에 도달하지 못함        → 반영 안 됨
② 서버가 처리했으나 응답이 유실됨     → 반영 됨
③ 서버가 처리 중 죽음                → 반영 여부 불명
```

**세 경우가 클라이언트에서 똑같이 보인다.** 타임아웃도, 끊긴 연결도, 예상과 다른 본문도
전부 ②일 수 있다. "에러가 났으니 안 됐겠지" 는 추론이 아니라 추측이다.

- `[실측]` 리다이렉트를 거치는 API 에서 특히 잘 드러난다. 처리는 첫 요청에서 끝나고 결과는 두 번째
  요청으로 받아오는 구조라면, 두 번째가 실패해도 **쓰기는 이미 완료**된 상태다.
- `[실측]` 유실 지점은 서버·네트워크만이 아니다. **응답을 받아오는 로컬 파이프라인**(원격 셸 래퍼,
  출력 필터)이 깨져도 클라이언트 입장에선 똑같이 "응답 없음"이다. 요청은 정상 완료됐는데
  출력 가공 단계의 오류로 결과를 못 본 사례가 실재한다.

## 확인하는 방법

재시도 전에 조회로 실제 상태를 본다. 조회는 안전하므로 몇 번을 해도 된다.

```
쓰기 → 응답 없음 → 조회 → 반영됐나?
                              ├ 예  → 재시도하지 않고 성공 처리
                              └ 아니오 → 그때 재시도
```

`[실측]` 2026-08-20 재현: 원격 셸 래퍼로 리소스 생성 API(POST)를 호출했는데 로컬 grep 패턴
오류로 파이프라인이 죽어 응답이 안 보였다 → 실패로 판단하고 같은 요청을 재실행 →
조회해 보니 **같은 이름의 리소스가 2개** 생성돼 있었다 (첫 요청도 성공했던 것). 정리 후
같은 상황에서 조회-선행으로 전환.

애초에 재시도가 안전하도록 설계할 수도 있다.

- **멱등키**: 요청마다 고유 키를 붙이고 서버가 같은 키의 중복 처리를 무시한다.
- **덮어쓰기 의미로 설계**: `추가` 대신 `이 값으로 설정` 이면 몇 번 해도 결과가 같다.
  이어붙이기(append)·증가(increment)는 본질적으로 재시도에 취약하다.

## 이 노트가 틀렸다면

- 응답 유실 상황에서 조회를 반복했을 때 **반영 안 됨이 일관되게 관측**되는 시스템이라면
  (예: 응답 커밋 전에는 쓰기를 확정하지 않는 동기 설계) → 그 시스템에는 ② 경로가 없다 —
  적용 범위에서 제외
- 서버가 모든 쓰기에 멱등키를 강제해 중복 요청이 항상 무시된다면 → "재시도가 중복을 만든다"
  는 함정이 그 API 에는 해당 없음

## 적용 범위

응답 채널이 처리와 분리될 수 있는 모든 쓰기 경로 — 리다이렉트형 API, 프록시/게이트웨이 경유,
원격 셸 래퍼처럼 **출력 전달 단계가 별도로 실패할 수 있는** 호출 방식 포함. 트랜잭션 커밋과
응답 전송이 원자적으로 묶인 시스템(그런 보장이 문서화된 경우)은 확인되지 않은 것으로 본다.

## 함정

- ⚠️ **로그에 실패로 남고 실제로는 성공한 상태가 제일 위험하다.** 사람이 로그를 보고
  수동 재실행하면 조용히 중복된다. 재시도 판단 근거를 로그가 아니라 상태 조회에 둔다.
- ⚠️ 유실 지점은 전송로 전체다 — 서버 응답이 정상이어도 **내 쪽 파이프(필터·래퍼)가 깨지면**
  같은 증상이 된다. "응답이 안 보인다"와 "요청이 실패했다"를 구분하는 것은 항상 조회다.
- 여러 건을 순차 처리하다 앞이 실패하면, 뒤 항목까지 싸잡아 "전부 다시" 하고 싶어진다.
  실패한 항목만 골라내지 않으면 성공했던 것들이 중복된다.
- 💡 자동 재시도를 켜기 전에 그 요청이 멱등한지 먼저 본다. 멱등하지 않은 요청의 자동 재시도는
  장애를 데이터 오염으로 바꾼다.

## 관련

- 분산 시스템에서 말하는 exactly-once 가 어려운 이유가 이것이다. 실제로 얻을 수 있는 것은
  at-least-once(중복 가능) 또는 at-most-once(누락 가능)이고, 멱등성이 있어야 앞의 것을
  뒤의 것처럼 다룰 수 있다.
