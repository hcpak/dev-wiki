# 소프트 삭제는 청소 명령을 따로 돌려야 사라진다

> 사용자가 지운 리소스는 `deleted=1` 로 표시만 될 뿐 행은 남는다. 삭제를 실제로 수행하는 것은 API 가 아니라 별도의 청소 명령이고, 그 명령은 아무도 자동으로 돌려주지 않는다.

**상태**: 활성
**마지막 검증**: 2026-08-13

## 왜 그렇게 동작하나

`[코드]` OpenStack 계열 서비스의 모델 대부분은 `SoftDeleteMixIn` 계열을 상속해 `deleted`(불리언) · `deleted_at`(시각) 컬럼을 갖는다. `DELETE` API 는 행을 지우지 않고 이 두 컬럼만 바꾼다.

```python
class Container(BASE, SoftDeleteMixIn, ModelBase):
    deleted    = sa.Column(sa.Boolean, nullable=False)
    deleted_at = sa.Column(sa.DateTime, nullable=True)
```

`[추정]` 이유는 두 가지로 보인다. 참조 무결성을 깨지 않고 지울 수 있고(자식 행이 남아 있어도 상관없다), 감사·복구 여지가 남는다. — 설계 의도를 명시한 업스트림 문서를 확인한 것은 아니다.

`[코드]` 대신 실제 삭제는 **관리 명령**의 몫이다. 서비스마다 이름이 다르지만 형태는 같다 — 보관 기간을 넘긴 `deleted=1` 행을 실제로 `DELETE` 하고, 부모가 사라져 고아가 된 자식 행을 함께 지운다.

```
$ <svc>-manage db clean --min-days 90   # 90일 지난 소프트 삭제 레코드를 실삭제
```

`[코드]` 여기서 함정이 시작된다. **이 명령은 패키지 설치만으로는 어디에도 등록되지 않는다.** cron 도 systemd timer 도 함께 깔리지 않는다. 운영자가 명시적으로 스케줄에 넣지 않으면 서비스 수명 내내 한 번도 실행되지 않고, 지워진 데이터는 영원히 남는다.

## 확인하는 방법

`[실측]` 가장 오래된 `deleted_at` 을 보면 청소가 돌았는지 한 번에 알 수 있다. **서비스 도입 시점에 가까우면 한 번도 안 돈 것이다.**

```sql
SELECT MIN(deleted_at) AS oldest, COUNT(*) AS cnt
FROM   <table>
WHERE  deleted = 1;
```

```
+---------------------+-------+
| oldest              | cnt   |
+---------------------+-------+
| 2016-05-16 09:59:21 | 51591 |
+---------------------+-------+
```

10년 치가 그대로 남아 있다는 뜻이다.

`[추정]` 부모 테이블만 보면 규모를 놓친다 — 암호화 페이로드나 메타데이터 같은 **자식 테이블이 같은 수만큼 딸려 있다.** 실제 정리량을 셀 때는 연관 테이블을 전부 UNION 해서 합산한다. — 자식 테이블 행 수를 실제로 세어본 출력은 남기지 않았다.

패키지에 스케줄이 들어 있는지는 이렇게 본다.

```
$ dpkg -L <pkg> | grep -E 'cron|timer'
$ systemctl list-timers --all | grep <svc>
```

## 이 노트가 틀렸다면

- **청소 명령을 한 번도 돌리지 않았는데 `MIN(deleted_at)` 이 최근 몇 달 안쪽이라면** → 어딘가에 자동 청소 경로가 있다는 뜻이다. 이 노트의 핵심 주장이 그 서비스에서는 거짓이다.
- **`dpkg -L | grep -E 'cron|timer'` 가 무언가를 출력한다면** → 패키지가 스케줄을 함께 설치하는 것이다. "운영자가 넣지 않으면 안 돈다" 가 그 패키지에는 해당하지 않는다.
- **소프트 삭제된 이름을 그대로 재사용해 리소스를 만들었는데 충돌 없이 성공한다면** → 유니크 제약을 점유한다는 `[추정]` 이 거짓이거나, 그 테이블의 유니크 인덱스에 `deleted` 컬럼이 포함돼 있다는 뜻이다.
- **자식 테이블 행 수가 부모와 크게 다르다면** → "같은 수만큼 딸려 있다" 는 `[추정]` 을 정리량 산정 근거로 쓸 수 없다.

## 적용 범위

- `SoftDeleteMixIn` 계열을 상속하는 OpenStack 서비스. 상속하지 않는 서비스는 `DELETE` 가 실제 삭제다.
- 데비안 계열 패키지 배포 기준. 컨테이너로 배포되면 `dpkg -L` 확인 자체가 의미 없고, 스케줄은 오케스트레이터 쪽(CronJob 등)에 있을 수 있다.
- 청소 명령의 이름·옵션은 서비스마다 다르다. `db clean` 이 아닌 경우가 많다.

## 함정

- ⚠️ `[추정]` **한 번도 안 돌린 DB 에 첫 실행을 운영에서 바로 하지 않는다.** 10만 행 단위 `DELETE` 가 한 트랜잭션으로 들어가면 락·복제 지연을 만든다. 보관 기간을 길게 잡아 조금씩 깎아 내려오거나, 검증 환경에서 소요 시간을 먼저 잰다. — 일반적인 DB 동작에서 유추한 것이고, 이 명령으로 실제 지연을 관측한 적은 없다.
- ⚠️ `[코드]` **"만료된 것 정리" 옵션과 "삭제된 것 정리" 옵션은 완전히 다른 기능이다.** 전자는 리소스의 유효기간 컬럼(`expiration`)을 보는데, 그 컬럼은 클라이언트가 값을 넣어줘야 채워진다. 값을 안 넣는 클라이언트가 대부분이면 이 옵션은 아무것도 하지 않는다. 옵션을 켜기 전에 `SELECT COUNT(*) WHERE expiration IS NOT NULL` 로 대상이 존재하는지부터 확인한다.
- ⚠️ `[추정]` **조회할 때만 채워지는 캐시 컬럼을 집계 기준으로 쓰지 않는다.** "참조된 적 있는 행"만 값이 있으므로 표본이 편향돼 있다. 전체 분포를 알려면 별도 채우기 배치가 먼저다 → [지연 실체화](lazy-activation-on-read.md)
- `[추정]` 소프트 삭제 행은 유니크 제약도 함께 차지한다. 같은 이름으로 다시 만들 때 충돌한다면 청소가 안 된 것을 의심한다. — 위 반증 조건 3번으로 확인할 수 있다.
