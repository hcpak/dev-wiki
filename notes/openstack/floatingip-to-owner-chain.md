# 공인 IP 하나로 소유자를 역추적하는 체인

> floating IP는 **자기가 누구 것인지 모른다**. 소유자를 알려면 `port_id`를 징검다리 삼아
> port → network → 인스턴스로 네 번 건너가야 하고, 그 체인은 중간에 끊길 수 있다.

## 왜 한 번에 안 나오나

`floatingip` 객체가 들고 있는 것은 사실상 이게 전부다.

| 필드 | 의미 |
| --- | --- |
| `floating_ip_address` | 외부에 노출되는 공인 IP |
| `fixed_ip_address` | 매핑된 사설 IP (문자열일 뿐, 어느 네트워크인지는 안 들어 있다) |
| `port_id` | **유일한 링크** — 이 IP가 꽂혀 있는 포트 |
| `tenant_id` | 소유 프로젝트 |

`fixed_ip_address`에 `<사설 IP>` 가 적혀 있어도 그것만으로는 아무것도 특정할 수 없다.
사설 대역은 프로젝트마다 겹치기 때문에, 같은 리전에 같은 사설 IP가 수백 개 존재한다.
**네트워크를 특정해 주는 것은 `port_id` 하나뿐이다.**

## 체인

```
floatingip
  └─ port_id ──▶ port
                  ├─ network_id ──▶ network  ( = VPC )
                  ├─ device_owner  ( 무엇이 물려 있나 )
                  └─ device_id ────▶ instance ( nova )
```

각 홉에서 얻는 것:

1. **floatingip → port** : `port_id`. 여기가 끊기면 그 아래는 전부 조회 불가.
2. **port → network** : `network_id`. 이 배포판 계열에서는 **network 객체가 곧 VPC**다
   (아래 참고). 그래서 여기서 이미 VPC가 확정된다.
3. **port → device_owner** : 붙어 있는 대상의 *종류*. `compute:<az>` 면 VM,
   `neutron:LOADBALANCERV2` 면 로드밸런서, `network:router_*` 면 라우터 내부 포트다.
4. **port → device_id → nova** : 인스턴스 UUID. 사람이 쓰는 서버 이름은 여기서만 나온다.
   neutron은 서버 이름을 모른다.

## 링크가 끊기는 지점 — `port_id`가 비어 있을 때

`port_id`가 빈 floating IP는 **어디에도 매핑되지 않은 공인 IP**다. 상태가 두 가지로 갈린다.

- **정상 미할당** — 고객이 IP만 확보해 두고 아직 붙이지 않은 것.
- **고아(orphan)** — 붙어 있던 자원이 사라졌는데 floating IP 레코드만 남은 것.

둘은 겉보기가 같아서 floating IP 목록만으로는 구분되지 않는다. 고아가 문제가 되는 이유는
정리 작업이 보통 **전체를 훑고 하나라도 실패하면 멈추는** 구조라, 레코드 하나가
그 프로젝트나 그 컨트롤러 경로 전체의 후속 처리를 막아버릴 수 있기 때문이다.
"IP 하나 남은 것뿐"이 아니다.

## 이 배포판에서 VPC = network 인 이유

VPC를 별도 테이블로 만들지 않고, 기존 network 객체에 **확장 필드를 얹는** 방식이다.

```
network-show <id>   →  일반 neutron 필드 + <vendor>:cidr 같은 확장 필드
vpc-show     <id>   →  같은 id 로 조회됨. cidrv4, routingtables, state ...
```

같은 UUID로 두 명령이 다 동작한다. VPC 상위 CIDR(`/16` 등)은 network 쪽 확장 필드로,
실제 할당 대역(`/24` 등)은 subnet에 있다. 그래서 **VPC CIDR과 subnet CIDR이 다른 게 정상**이고,
둘을 같은 것으로 보면 IP 계산이 어긋난다.

이 구조 덕분에 역추적이 짧아진다. `port.network_id`를 얻는 순간 VPC가 나오므로
subnet을 거쳐 VPC를 되짚을 필요가 없다.

## 서버 이름이 목록에 안 나올 때 — 관리형 서비스의 숨은 테넌트

한 VPC 안의 VM 목록을 뽑았는데 **포트 개수보다 서버 개수가 적게** 나오는 일이 있다.
포트는 10개인데 서버 목록은 5개인 식이다.

원인은 대개 **관리형 서비스(예: 관리형 쿠버네티스)가 자기 전용 테넌트로 VM을 만들기** 때문이다.
고객 프로젝트 정보에 `kubernetes_tenant_id` 같은 별도 테넌트 ID가 붙어 있고,
컨트롤플레인 노드들은 그 테넌트 소유다. 네트워크는 고객 VPC를 공유하지만
**소유권은 다른 테넌트**라, 고객 프로젝트로 필터링한 서버 목록에서 통째로 빠진다.

> 포트 수와 서버 수가 안 맞으면 조회 실패를 의심하기 전에 **부속 테넌트를 먼저 의심**한다.
> 프로젝트 상세의 `*_tenant_id` 계열 필드가 단서다.

## 조회가 타임아웃될 때

`server list --all-projects --project <id>` 형태는 리전 전체를 훑은 뒤 필터링하는 경로를 타서,
운영 규모에서는 수십 초~분 단위로 늘어진다. 대안은 두 가지다.

- **테넌트 지정 목록 + 최소 컬럼** — 상세 필드(`--long` 등)를 빼면 응답이 급격히 짧아진다.
  느린 건 목록 자체가 아니라 서버마다 부가 정보를 채우는 단계인 경우가 많다.
- **UUID로 개별 조회** — 이미 `device_id`를 알고 있다면 개별 show가 목록보다 훨씬 빠르다.
  포트 목록에서 device_id를 확보했으므로 이 경로가 대체로 유리하다.

원격 실행 래퍼에 고정 타임아웃이 걸려 있다면, 원격 쪽에서 명령마다
`timeout N` 을 씌워 **한 명령이 전체 예산을 다 먹지 않게** 나눠 두면 부분 결과라도 건진다.
