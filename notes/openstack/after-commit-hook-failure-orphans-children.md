# 커밋 이후 훅에서 실패하면 자식 레코드가 고아로 남는다

> `AFTER_DELETE` 류의 훅은 주 트랜잭션이 **커밋된 뒤** 실행된다. 훅 안에서 예외가 나도 주 삭제는 되돌아가지 않아, 사라진 부모를 참조하는 자식 행이 남는다. 그 뒤 부모 리소스의 삭제 API 는 그 참조를 조회하다 `NotFound` 로 **영구 실패**한다.

**상태**: 활성
**마지막 검증**: 2026-08-14

## 왜 그렇게 동작하나

`[코드]` 플러그인이 리소스 삭제에 후처리를 붙이는 전형적인 구조다.

```python
def _after_delete_parent(self, resource, event, trigger, context, parent, **kwargs):
    self._mark_children_inactive(context, parent['id'])   # ① 통지 포함
    self._delete_children(context, parent)               # ② 자식 행 삭제
```

- `[코드]` `AFTER_*` 는 이름 그대로 **커밋 이후** 이벤트다. 여기서 예외가 나도 부모 삭제는 이미 확정돼 있다.
- `[추정]` 프레임워크는 콜백 예외를 로깅만 하고 넘어가는 경우가 많다. — 콜백 레지스트리 구현을 전부 확인한 것은 아니다.
- `[코드]` ① 이 에이전트 통지를 포함하면, 담당 에이전트 바인딩이 없거나 통지가 실패할 때 예외가 난다. 그러면 **② 가 아예 실행되지 않는다.**
- 결과: 자식 행은 남고 그 `parent_id`(또는 `port_id` 같은 참조 컬럼)는 존재하지 않는 대상을 가리킨다.

여기서 끝나면 쓰레기 한 줄이지만, 삭제 경로가 그 참조를 **무조건 조회**하면 문제가 커진다.

```python
for child in children:
    target = self.plugin.get_target(context, child['target_id'])  # NotFound
    self._delete_child(context, child, target)
```

`[실측]` 대상이 되살아날 수 없으므로 부모 삭제는 **재시도해도 항상 실패**한다. 자기 치유 경로가 없는 영구 실패다. — 실제 환경에서 삭제 API 가 반복 실패하는 리소스를 확인했고, 참조 컬럼이 존재하지 않는 대상을 가리키는 것이 원인으로 확정됐다.

## 확인하는 방법

`[실측]` 자식 테이블의 참조 컬럼을 실제 대상 목록과 대조한다. 한 줄이라도 나오면 고아다.

```bash
comm -23 <(<자식 목록 조회> | awk '{print $N}' | sort -u) \
         <(<대상 목록 조회> | awk '{print $N}' | sort -u)
```

- ⚠️ 대상 목록을 뽑을 때 **관리자 범위로 전부** 조회해야 한다. 프로젝트 범위로만 뽑으면 남의 리소스가 목록에서 빠져 정상 행까지 "고아"로 잡힌다(실제로 이 실수로 전량이 고아로 보였다).
- 재현 실험을 하려면 정상 경로로는 안 된다 — 아래 함정 참고. DB 에서 참조 컬럼을 존재하지 않는 값으로 바꾸면 같은 상태를 만들 수 있다.

## 이 노트가 틀렸다면

- **통지가 실패했는데도 자식 행이 남지 않는다면** → ② 가 ① 의 성공에 매여 있지 않다는 뜻이다. 이 노트의 인과 사슬이 그 구현에는 성립하지 않는다.
- **부모 삭제를 재시도했더니 성공한다면** → 어딘가에 자기 치유 경로(참조 재생성, 조회 생략 분기)가 있다는 뜻이고, "영구 실패" 주장이 거짓이다.
- **정상 조작만으로 고아 상태가 재현된다면** → "정상 경로로는 재현 불가" 가 거짓이다. 그렇다면 통지 실패 말고 다른 유입 경로가 있다는 뜻이므로 원인 분석을 다시 해야 한다.
- **정합성 도구를 돌렸더니 고아 행이 실제로 사라진다면** → "복구 수단이 없다" 가 거짓이다. 그 도구를 표준 처방으로 올릴 수 있다.

## 적용 범위

- 콜백 레지스트리에 `AFTER_*` 이벤트로 후처리를 다는 OpenStack 계열 플러그인. `BEFORE_*` 나 `PRECOMMIT_*` 에 붙인 훅은 트랜잭션 안에서 돌므로 이 노트가 해당하지 않는다.
- 자식 행을 지우는 경로가 **참조 대상을 먼저 조회**하는 구현. 조회 없이 지우면 고아 행이 남더라도 삭제 API 는 성공한다.

## 함정

- ⚠️ `[코드]` **광범위 `except` 가 원인을 지운다.** 삭제 함수가 `except Exception` 으로 전부 잡아 "삭제 실패" 하나로 변환하면, 로그에 원인이 debug 로만 남거나 아예 사라진다. 사용자는 충돌 상태 코드만 보고 원인을 알 수 없다.
- ⚠️ `[실측]` **정상 조작으로는 재현되지 않는다.** 부모를 만들고 참조 대상을 지우는 순서를 그대로 밟아도, 통지가 성공하는 정상 환경에서는 훅이 자식 행까지 잘 지운다. 재현 절차를 요구받으면 **절차를 줄 수 없는 종류의 결함**이라는 점을 먼저 밝히고, 이미 그 상태로 남아 있는 리소스로 검증하는 편이 정확하다.
- ⚠️ `[추정]` **동기화·롤백 도구가 도움이 안 될 수 있다.** 정합성 도구가 "삭제 대상"을 계산해 **로그로만 남기고 실제로 지우지 않거나**, 정리 전에 참조 대상을 먼저 조회해 고아 항목을 건너뛰면 복구 수단이 없다. — 도구 코드를 끝까지 읽어 확인한 것은 아니다. 위 반증 조건 4번으로 확인할 수 있다.
- 💡 부모 상태만 바뀌고(예: `INACTIVE`) 자식이 남았다면 ① 은 성공하고 ② 에서 끊긴 것이다. 어느 단계에서 멈췄는지 상태값으로 역추적할 수 있다.

## 처방

- 삭제 경로에서 **참조 대상 `NotFound` 는 정상 흐름으로 취급**한다. 통지는 건너뛰고(알릴 대상이 이미 없다) 자식 행만 지우고 계속 진행한다. 예외 종류는 좁게 잡아, 다른 실패를 조용히 삼키지 않게 한다.
- 뭉개는 `except` 는 남겨도 **원인을 error 레벨 + 스택으로** 올린다. API 응답은 어차피 하나뿐이라 로그가 유일한 단서다.
- 근본 대책은 훅 쪽이다. 통지 실패와 무관하게 자식 정리를 보장할지(재시도·정리 큐), 아니면 커밋 전 이벤트로 옮길지 결정해야 한다.
