# SNI 가 필요한 이유 — 인증서를 골라야 할 때 `Host:` 헤더는 아직 오지 않았다

> IP 하나에 도메인 여러 개가 물린 HTTPS 서버는 **`Host:` 헤더로 인증서를 고를 수 없다.**
> TLS 협상(인증서 제시)이 HTTP 요청보다 **먼저** 끝나야 하고, `Host:` 헤더는 그 인증서로 연
> 암호화 채널 **안**에 들어 있기 때문이다. SNI 는 목적지 도메인명을 ClientHello 에 **평문으로**
> 얹어 이 닭-달걀을 끊는다.

## 왜 그렇게 동작하나

### 순서가 문제의 전부다

`[문서]` 접속은 이 순서로 진행된다.

```
1. TCP 연결
2. TLS 협상        ← 서버가 인증서를 여기서 내민다
3. 암호화 채널 확립
4. GET / HTTP/1.1
   Host: app.example.com    ← Host 헤더는 여기서야 도착한다
```

서버가 인증서를 선택해야 하는 시점은 **2번**이고, 목적지 도메인을 알려주는 `Host:` 헤더는
**4번**에 온다. 게다가 4번은 3번에서 열린 암호화 채널 안이라, 그 채널을 열려면 인증서가 필요하고
인증서를 고르려면 채널 안을 봐야 하는 순환이 생긴다.

### SNI 는 이 순환을 끊는 우회로다

`[문서]` 클라이언트는 2번의 첫 메시지(ClientHello)의 확장 필드에 **"나 `app.example.com` 에 왔다"**
를 적어 보낸다. 아직 암호화 전이므로 **평문**이다. 서버는 그것을 읽고 매칭되는 인증서를 꺼낸다.

이 덕분에 **IP 하나 + 포트 하나에 서로 다른 도메인의 인증서 여러 장**을 올릴 수 있다.
가상 호스팅이 HTTPS 에서도 가능해진 근거가 이것 하나다.

### SNI 를 안 보내면 어떻게 되나

`[문서]` 서버는 **미리 정해둔 기본 인증서**를 꺼낸다. 클라이언트가 부른 이름과 그 인증서의 이름이
다르면 인증서 불일치 경고가 난다. 실패가 아니라 **"기본값으로 조용히 대체"** 라는 점이 중요하다 —
설정이 틀렸어도 서버는 정상 동작한 것처럼 보인다.

## 확인하는 방법

`[추정]` 아래 명령 형태는 표준 `openssl` 사용법이지만, 이번에 직접 실행해 출력을 보지는 않았다.

**① SNI 를 보냈을 때** — `-servername` 으로 명시한다:

```bash
openssl s_client -connect <vip>:443 -servername app.example.com </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -dates
```

**② SNI 를 안 보냈을 때** — `-noservername` 으로 뺀다. 기본 인증서가 나온다:

```bash
openssl s_client -connect <vip>:443 -noservername </dev/null 2>/dev/null \
  | openssl x509 -noout -subject
```

①과 ②의 `subject` 가 **다르게** 나오면 SNI 기반 선택이 실제로 동작하는 것이다.
같게 나오면 인증서가 한 장뿐이거나 SNI 매칭이 안 되고 있다.

**③ 평문으로 나가는지 직접 본다** — ClientHello 를 캡처하면 도메인명이 그대로 보인다:

```bash
tcpdump -i <if> -nn -A "tcp port 443 and tcp[((tcp[12:1]&0xf0)>>2):1] = 0x16"
```

## 이 노트가 틀렸다면

- ①과 ② 의 인증서 `subject` 가 **항상 같다** → 그 서버는 인증서 선택에 SNI 를 쓰지 않는다(단일 인증서 구성)
- ClientHello 캡처에서 도메인명이 **안 보인다** → 클라이언트가 SNI 를 안 보냈거나, ECH(Encrypted Client Hello)가
  적용되어 암호화된 것이다. 후자면 "평문" 이라는 이 노트의 서술이 그 환경에서 깨진다
- `Host:` 헤더만으로 인증서를 고르는 구현이 관측된다 → TLS 종료 지점이 앞단에 따로 있어
  실제 인증서 선택은 거기서 이미 끝난 경우다. 적용 범위가 좁아진다

## 적용 범위

- TLS 1.2 / 1.3 의 일반적인 구성. **ECH 가 켜지면 SNI 가 암호화**되어 "평문" 서술이 성립하지 않는다
- HTTPS 뿐 아니라 TLS 위에 올라가는 프로토콜 전반에 해당한다
- 프록시가 TLS 를 앞단에서 종료하는 구성에서는, 뒷단은 이미 평문을 받으므로 이 문제가 없다

## 함정

- ⚠️ **와일드카드 인증서는 한 레벨만 덮는다.** `*.example.com` 은 `app.example.com` 은 되지만
  `a.b.example.com` 은 안 된다. SNI 매칭은 되는데 검증에서 떨어진다
- ⚠️ **SNI 는 평문이라 도청자에게 "어느 사이트에 접속하는지" 가 그대로 보인다.** 암호화되는 것은
  내용이지 목적지 이름이 아니다. ECH 는 이걸 가리려는 것이다
- ⚠️ **SNI 미전송 클라이언트는 실패하지 않고 기본 인증서를 받는다.** 그래서 기본 인증서 설정이
  틀려도 대부분의 브라우저에서는 멀쩡해 보이고, 오래된 클라이언트 한 종류에서만 터진다
- 💡 도메인을 이전하며 DNS 만 새 이름으로 돌린 경우, 인증서는 옛 이름 기준으로 남아 있게 된다.
  이때 새 인증서를 **추가**하는 것으로 대응되지만 **기본 인증서는 여전히 옛 것**이라는 점을 놓치기 쉽다
