# 자물쇠가 정상인데 404 — TLS 판정과 L7 라우팅은 다른 계층에서 따로 걸린다

> 브라우저 자물쇠가 멀쩡한데 404 가 뜨는 건 모순이 아니다. **TLS 는 SNI 로, L7 라우팅은 `Host:` 헤더로,
> 서로 다른 시점에 서로 다른 설정을 보고 판정한다.** 두 관문이 독립이라 앞은 통과하고 뒤에서 떨어질 수 있다.
> 도메인을 옮기며 인증서만 맞추고 라우팅 규칙을 놓치면 정확히 이 증상이 나온다.

## 왜 그렇게 동작하나

### 같은 도메인명을 두 번, 다른 설정으로 대조한다

`[코드]` 프록시는 요청 하나를 처리하며 도메인명을 두 번 본다.

| | 언제 | 무엇을 보나 | 무엇과 대조하나 | 실패하면 |
| --- | --- | --- | --- | --- |
| TLS 판정 | 핸드셰이크 | ClientHello 의 **SNI** | 등록된 인증서 목록 | 인증서 불일치 경고 |
| L7 판정 | 요청 처리 | HTTP **`Host:` 헤더** | L7 라우팅 규칙 | 404 · 503 · 엉뚱한 백엔드 |

값은 보통 같지만 **참조하는 설정이 완전히 별개**다. 인증서를 추가해도 라우팅 규칙은 안 바뀌고,
라우팅 규칙을 고쳐도 인증서는 안 바뀐다.

### 그래서 이런 상태가 성립한다

```
SNI  = app.example.net  →  *.example.net 인증서 매칭   ✅  자물쇠 정상
Host = app.example.net  →  규칙은 example.com 만 알고 있음  ❌  404
```

**자물쇠는 "암호화가 제대로 됐다" 는 뜻이지 "요청이 목적지에 도달했다" 는 뜻이 아니다.**
브라우저는 첫 번째 관문의 결과만 자물쇠로 표시하고, 두 번째 관문의 결과는 본문에 실려 온다.

### DNS 만 돌린 이전에서 특히 잘 터진다

`[추정]` 기존 서비스를 새 도메인으로 옮길 때 DNS 만 새 이름 → 같은 IP 로 바꾸는 방식이 흔하다.
손이 적게 가지만, **프록시 설정은 옛 이름 기준으로 그대로 남는다.** 옛 이름을 전제로 한 곳이
최소 두 군데(인증서, 라우팅 규칙)라서, 눈에 띄는 인증서만 고치고 라우팅을 놓치는 순서로 진행되기 쉽다.

## 확인하는 방법

`[추정]` 아래 명령은 표준 사용법이지만 이번에 실행해 출력을 보지는 않았다.

**① 두 관문을 분리해서 본다** — TLS 만 확인:

```bash
openssl s_client -connect <vip>:443 -servername app.example.net </dev/null 2>/dev/null \
  | openssl x509 -noout -subject
```

**② L7 만 확인** — TLS 를 우회해 평문 포트로 `Host:` 헤더만 바꿔 넣는다:

```bash
curl -sS -o /dev/null -w '%{http_code}\n' -H 'Host: app.example.net'  http://<vip>/
curl -sS -o /dev/null -w '%{http_code}\n' -H 'Host: app.example.com'  http://<vip>/
```

**옛 이름은 200, 새 이름은 404** 로 갈리면 라우팅 규칙이 원인이라는 게 확정된다.
①이 정상인데 ②가 갈린다면 인증서는 무죄다.

**③ 규칙에 걸린 호스트 조건을 직접 본다:**

```bash
grep -n -iE "hdr\(host\)|req\.hdr\(host\)" <cfg>
```

## 이 노트가 틀렸다면

- ②에서 **두 `Host:` 값 모두 같은 응답**이 나온다 → 호스트 기반 라우팅이 없는 구성이다.
  404 의 원인은 다른 곳(경로 규칙·백엔드 애플리케이션)이며 이 노트는 그 사례에 적용되지 않는다
- ①이 **실패하는데도** 브라우저 자물쇠가 정상이다 → 중간에 다른 TLS 종료 지점이 있다.
  "두 관문이 같은 장비에 있다" 는 전제가 깨진다
- SNI 와 `Host:` 가 **불일치할 때 프록시가 요청을 거부한다** → 그 구성에서는 두 판정이 독립이 아니다.
  적용 범위가 좁아진다

## 적용 범위

- TLS 를 종료하고 L7 라우팅을 수행하는 프록시·로드밸런서 구성
- TLS 패스스루(`mode tcp`)에는 해당하지 않는다 — 애초에 `Host:` 헤더를 볼 수 없어 L7 판정 자체가 없다
- HTTP/2 · HTTP/3 에서는 `Host:` 대신 `:authority` 의사 헤더를 보지만 **구조는 같다**

## 함정

- ⚠️ **자물쇠를 보고 "TLS 설정은 끝났다" 로 판단하면 남은 절반을 못 본다.** 인증서 작업과
  라우팅 작업은 같이 계획해야 한다
- ⚠️ **SNI 와 `Host:` 는 서로 다를 수 있다.** 클라이언트가 마음대로 정하는 값이라 일치가 보장되지 않는다.
  둘 중 하나로만 접근 제어를 하면 다른 하나로 우회된다
- ⚠️ **증상이 404 라 애플리케이션 문제로 오인되기 쉽다.** 프록시가 라우팅에 실패해 낸 404 와
  백엔드가 낸 404 는 겉보기가 같다. 응답 헤더나 접근 로그에서 어느 쪽이 냈는지부터 가른다
- 💡 도메인 이전 체크리스트는 최소 세 칸이다 — **DNS · 인증서 · 라우팅 규칙.**
  앞의 둘만 하고 끝내는 게 이 노트가 다루는 실패다
