# anycast 는 패킷을 복제하지 않는다 — 목적지를 라우터가 고를 뿐이다

> 같은 IP 를 여러 지점에 설정한다는 말 때문에 "여러 곳에 동시에 쏜다" 로 읽히지만, 정반대다.
> anycast 패킷은 **딱 한 곳에만** 도착한다. 복제는 broadcast·multicast 에서 일어나고,
> anycast 에서는 전달 방식이 아니라 **경로 선택**만 달라진다. 보내는 호스트는 자기가 unicast 를
> 보내는지 anycast 를 보내는지 알 방법이 없다 — 선택은 전적으로 중간 라우터가 한다.

## 왜 그렇게 동작하나

`[문서]` IPv6 는 RFC 4291 에서 anycast 를 주소 종류로 정의한다. "둘 이상의 인터페이스에 할당되고,
전달되는 패킷은 라우팅 프로토콜의 거리 척도상 가장 가까운 하나에게 간다."

`[문서]` IPv4 에는 그런 주소 종류가 없다. 같은 프리픽스를 여러 지점에서 각자 BGP 로 광고하는
**운영 관행**으로 구현한다. 그래서 IPv4 anycast 는 프로토콜 기능이 아니라 라우팅 구성이다.

`[코드]` 복제가 일어날 지점이 구조적으로 없다. 각 라우터는 하나의 목적지 프리픽스에 대해
BGP 최적 경로 선택으로 **경로 하나**만 FIB 에 올린다. ECMP 가 켜져 있으면 넥스트홉이 여러 개
올라가지만, 개별 패킷은 여전히 해시로 고른 넥스트홉 **하나로만** 나간다. 어느 쪽이든 패킷이
둘로 늘어나는 단계가 없다. (라우팅 테이블 구조에서 추론 — 실제 FIB 덤프는 보지 않음)

네 가지 전달 방식을 비교하면 anycast 만 계층이 다르다.

| 방식 | 목적지 | 패킷 복제 | 결정 주체 |
| --- | --- | --- | --- |
| unicast | 주소를 가진 그 한 대 | 없음 | 주소 자체 |
| broadcast | 같은 링크의 전원 | **있음** (L2 플러딩) | 브로드캐스트 도메인 경계 |
| multicast | 그룹에 가입한 노드들 | **있음** (분기점에서) | 수신자의 가입 의사 |
| anycast | 같은 주소를 광고하는 N곳 중 1곳 | 없음 | **중간 라우터의 경로 선택** |

CDN 이 anycast 를 쓰는 이유가 여기서 나온다. 사용자를 가까운 지점으로 보내는 일을
애플리케이션이나 DNS 가 아니라 **인터넷 라우팅이 대신 해준다**. 별도의 유도 로직 없이
프리픽스를 각 지점에서 광고하기만 하면 된다.

## 확인하는 방법

공개 anycast 주소에 서버 식별자를 물으면, 같은 IP 인데 **응답한 지점의 이름**이 돌아온다.

```
$ dig +short CHAOS TXT id.server @1.1.1.1
"icn06"

$ dig +short CHAOS TXT id.server @9.9.9.9
"res700.itm"
```

`icn06` 은 인천(ICN), `itm` 은 오사카 이타미(ITM) 공항 코드다. 두 사업자가 같은 anycast 기법을
쓰는데도 이 위치에서 가장 가까운 지점이 서로 다르다 — 각자의 지점 분포와 BGP 경로가 다르기 때문이다.

복제가 없다는 것은 응답 개수로 확인한다. 보낸 만큼만 돌아오고 `DUP!` 이 붙지 않는다.

```
$ ping -c 4 1.1.1.1
--- 1.1.1.1 ping statistics ---
4 packets transmitted, 4 packets received, 0.0% packet loss
round-trip min/avg/max/stddev = 6.202/19.206/38.528/12.104 ms
```

RTT 최소 6.2ms 는 국제 회선 왕복 시간이 아니다. traceroute 로도 공인 구간 첫 홉이 5.8ms 로,
전 세계에 하나뿐인 서버가 아니라 **바로 근처의 지점**이 답하고 있다는 뜻이다.

```
$ traceroute -n 1.1.1.1
 1  <사설 IP>   5.056 ms
 ...
11  <공인 홉>   5.821 ms
```

## 이 노트가 틀렸다면

- `ping` 응답에 `DUP!` 이 붙는다 → **복제가 없다는 주장이 깨진다.** 그 주소는 anycast 가 아니라
  broadcast·multicast 이거나, 경로에 패킷을 복제하는 장비가 있다
- 다른 대륙에서 같은 `id.server` 질의를 했는데 응답이 동일하게 `icn06` 이다 → 그 주소는
  anycast 가 아니라 단일 지점 unicast 다. 위치에 따라 답이 달라지는 것이 anycast 의 정의다
- 한 세션 도중 `id.server` 응답이 바뀐다 → 경로가 수렴하지 않고 흔들리는 것이고,
  아래 `함정` 의 TCP 세션 절단 우려가 실재한다는 근거가 된다
- IPv4 전용 anycast **주소 종류**를 정의한 RFC 가 나온다 → "IPv4 는 BGP 운영 관행일 뿐" 이라는
  서술이 틀린 것이다

## 적용 범위

- 측정 시점 2026-09-17, 국내 한 사업자망의 egress 한 곳. **다른 AS·다른 대륙에서는 응답 지점이 다르다** —
  그게 정상이고, 오히려 이 노트의 주장을 확인해주는 결과다
- `hostname.bind` / `id.server` 는 사업자가 응답해 줄 때만 쓸 수 있다. Google 의 `8.8.8.8` 은
  이 질의에 빈 응답을 준다 — 지점을 노출하지 않는 운영자도 있다
- ECMP 구간에서는 5-tuple 해시로 넥스트홉이 갈린다. 흐름이 여러 경로로 나뉠 수는 있어도
  **패킷 하나가 복제되지는 않는다**

## 함정

- ⚠️ `[추정]` 경로가 바뀌면 진행 중인 흐름이 다른 지점으로 꽂혀 TCP 세션이 끊긴다(RST).
  anycast 가 UDP 기반 DNS 에서 먼저 자리잡고, CDN 이 anycast 만 쓰지 않고 DNS 기반 유도를
  섞는 이유로 설명된다. **경로 절체 중 세션 절단을 직접 관측하지는 않았다**
- **"IP 그룹" 은 표준 프로토콜 용어가 아니다.** RFC 에 그런 정의가 없는데, 세 가지 다른 것이
  이 이름으로 불린다. 대화에서 이 말이 나오면 어느 쪽인지 되물어야 한다.

  | 실제 개념 | 정확한 이름 | 패킷 전달과의 관계 |
  | --- | --- | --- |
  | 같은 주소를 공유하는 노드 집합 | anycast group | 하나만 받는다 |
  | 그룹 주소로 보내면 가입자 전원이 받음 | multicast group (IGMP) | 복제된다. "그룹" 을 쓰는 유일한 표준 개념 |
  | 방화벽·ACL 룰에서 IP 목록을 이름으로 묶은 것 | 벤더별 주소 객체 | **무관.** 설정 편의용일 뿐 |

  세 번째가 함정이다. 유일하게 제품 UI 에 `IP Group` 이라고 그대로 쓰여 있어서 이 말을 들으면
  먼저 떠오르는데, 정작 패킷이 어디로 가는지와는 아무 상관이 없다.
- "스위치에 물려 있는 전부" 는 **브로드캐스트 도메인**이고, IP 관점에서는 **서브넷**이다.
  이걸 그룹이라고 부르지 않고 `192.0.2/24` 처럼 프리픽스로 지칭한다
- `[문서]` anycast 응답 지점은 자기가 가장 가깝다는 것을 **모른다**. 선택은 중간 라우터가 끝낸
  뒤이고 패킷에는 그 흔적이 없다. "왜 이 트래픽이 하필 우리 지점으로 왔나" 를 알려면
  서버 로그가 아니라 BGP 광고 상태를 봐야 한다
