# `100.64.0.0/10` — 공인도 사설도 아닌 제3의 대역

> RFC 6598 "Shared Address Space". **사업자 내부 전용** 대역이라,
> 고객이 쓰는 RFC 1918 사설 대역과 겹칠 걱정 없이 인프라 내부 주소로 쓸 수 있다.

## 왜 따로 만들었나

캐리어 등급 NAT(CGNAT)를 하려면 사업자가 가입자와 자기 NAT 장비 사이에 쓸 주소가 필요하다.
기존 선택지는 둘 다 문제가 있었다.

| 선택지 | 문제 |
| --- | --- |
| 공인 IP | 그럴 거면 NAT를 할 이유가 없다. IPv4 고갈이 애초의 동기다 |
| RFC 1918 (`10/8`, `172.16/12`, `192.168/16`) | **고객이 이미 쓰고 있다.** 겹치면 라우팅이 깨진다 |

그래서 "공인처럼 유일하되 인터넷으로는 라우팅되지 않는" 대역을 새로 잘라낸 것이 `100.64.0.0/10`
(= `100.64.0.0` ~ `100.127.255.255`, 약 400만 개)이다.

## 성질

- **인터넷으로 라우팅되지 않는다.** 사업자 경계 밖으로 나가지 않는다.
- **RFC 1918과 겹치지 않는다.** 고객 사설망이 `10/8` 전체를 쓰고 있어도 충돌하지 않는다.
- **고객에게 판매·노출되는 주소가 아니다.** 인프라 내부 배관용이다.
- 사설 대역이 아니므로 일부 방화벽·보안 장비의 "private 주소" 규칙에 **안 걸린다.** 룰을 쓸 때 주의.

## 클라우드에서 마주치는 곳

포트나 인스턴스 속성에 `100.64.x.x` 가 붙어 있으면 대개 **오버레이 아래쪽 배관**이다.

- SNAT 게이트웨이가 아웃바운드 트래픽에 씌우는 내부 주소
- 하이퍼바이저 ↔ 네트워크 노드 사이의 내부 홉
- 관리형 서비스가 고객 VPC를 침범하지 않고 통신하기 위해 쓰는 경로

고객 VPC CIDR이 `192.168/16` 인데 포트 속성에 `100.64.x.x` 가 보인다면,
그건 고객 대역에 속한 주소가 아니라 **인프라가 그 포트에 부여한 내부 주소**다.
고객 라우팅 테이블이나 보안그룹에서 찾으려 하면 나오지 않는다.

## 헷갈리기 쉬운 이웃 대역

| 대역 | 정체 |
| --- | --- |
| `100.64.0.0/10` | RFC 6598 공유 주소 공간 (여기서 다루는 것) |
| `169.254.0.0/16` | 링크 로컬. 클라우드 메타데이터 서비스(`169.254.169.254`)가 여기 산다 |
| `198.18.0.0/15` | 벤치마크 테스트 전용 (RFC 2544) |
| `192.0.2/24` 등 | 문서용 예시 주소 (RFC 5737) |

앞의 두 개는 실제 트래픽이 흐르고, 뒤의 두 개는 흐르면 안 되는 주소다.
