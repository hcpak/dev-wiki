# 한 세션은 모델을 하나만 갖는다 — 서브에이전트가 티어를 바꾸는 유일한 통로다

> 에이전트 CLI 에서 모델은 세션 단위로 고정된다. 그래서 "쉬운 일은 싼 모델, 어려운 일은 비싼 모델"을
> 한 대화 안에서 실현하려면 작업을 **서브에이전트로 내보내는 것 말고는 방법이 없다.**
> 추론 강도(effort)는 한 걸음 더 제약이 심해서, 호출 인자로 넘길 수 없고 에이전트 정의 파일에만 박힌다.

## 왜 그렇게 동작하나

`[문서]` 메인 루프의 모델·effort 는 그 턴에만 바꿀 수 있고 지속되지 않는다. 다음 프롬프트에서 세션 기본값으로 돌아간다.
그래서 대화 도중 "이 작업만 싼 모델로" 는 성립하지 않는다 — 바꾸면 세션 전체가 바뀐다.

`[문서]` 서브에이전트는 자기 정의 파일의 프론트매터(`model`, `effort`)로 고정 실행된다.
메인이 최상위 티어여도 그 안에서 호출한 서브에이전트는 자기 파일에 적힌 티어로 돈다.
이것이 한 세션 안에 두 개 이상의 티어를 공존시키는 유일한 경로다.

`[문서]` **`model` 은 호출 시 오버라이드할 수 있지만 `effort` 는 못 한다.**
그래서 "리뷰는 상위모델/최고effort, 패치는 상위모델/중간effort" 같은 조합은
**에이전트를 미리 만들어 두는 것 외에 얻을 방법이 없다.** 티어 프리셋을 파일로 굳혀두는 설계가 여기서 나온다.

`[문서]` 절감 효과는 두 겹이다. 비용(대량 읽기를 싼 티어가 처리)과 **메인 컨텍스트**(중간 산출물이
메인 대화에 안 쌓임)다. 후자가 종종 더 크다 — 검색 결과 수백 줄이 아니라 결론 한 줄만 메인에 남는다.

### 싼 티어로 내리면 항상 싸지는가 — 아니다

`[문서]` 벤치마크 근거로 세 가지가 보고돼 있다.

1. **속도의 주 레버는 모델 크기가 아니라 effort 다.** 같은 effort 면 티어 간 지연이 비슷하다.
   속도를 원하면 모델을 낮추기 전에 effort 를 낮추는 쪽이 맞다.
2. **도구 호출이 많은 작업은 약한 모델이 더 비싸다.** 시행착오로 tool 호출·토큰·시간이 늘어난다
   (한 A/B 에서 중간 티어가 상위 티어 대비 tool 호출 2.9배, 58% 느림, 품질은 동등).
3. 순수 생성·기계적 작업에서만 싼 티어가 토큰이 적고 빠르다.

`[추정]` 그래서 "조회·검색은 최저 티어" 는 안전한 규칙이지만, "코드 편집도 싼 티어로" 는
도구 루프가 길어지는 순간 절감이 사라지거나 역전될 수 있다.

## 확인하는 방법

에이전트 정의 파일에 티어가 박혀 있는지 본다.

```
$ head -8 <에이전트 디렉터리>/reviewer.md
---
name: reviewer
description: |
  코드/보안 리뷰 전용 (읽기 전용). ...
tools: Read, Grep, Glob, Bash, WebFetch, Skill
model: opus
effort: xhigh
```

같은 디렉터리의 다른 에이전트가 서로 다른 조합을 들고 있으면, 프리셋 설계가 맞다는 신호다.

```
$ grep -H -E '^(model|effort):' <에이전트 디렉터리>/*.md
chore-runner.md:model: haiku
chore-runner.md:effort: low
patcher.md:model: opus
patcher.md:effort: medium
reviewer.md:model: opus
reviewer.md:effort: xhigh
```

## 이 노트가 틀렸다면

- **호출 인자로 `effort` 를 넘겼는데 그대로 반영되면** → "effort 는 파일에서만 온다"가 틀렸다.
  프리셋 에이전트를 미리 만들어 둘 이유가 사라지고, 호출 시점에 조합하면 된다.
- **세션 중 모델을 바꾸는 명령이 다음 프롬프트까지 유지되면** → "세션 단위 고정"이 틀렸다.
  서브에이전트를 거치지 않고 메인에서 구간별로 티어를 갈아끼울 수 있다는 뜻이다.
- **도구 집약 작업에서 싼 티어의 tool 호출 수가 상위 티어와 비슷하게 나오면** → 위 2번이
  모델·과제 조합에 종속된 관측이라는 뜻이고, "약한 모델이 더 비싸다"의 적용 범위가 좁아진다.
- **서브에이전트 정의 파일에 티어를 적었는데 메인 모델로 실행되면** → 프리셋 자체가 안 먹는 것이므로
  이 노트의 전제가 통째로 무너진다.

## 적용 범위

- 서브에이전트를 정의 파일(프론트매터)로 선언하는 방식의 에이전트 CLI 기준.
- 티어 이름·effort 단계 수는 제품마다 다르다. 여기서 참조한 effort 는 5단계(low → max).
- 벤치마크 수치는 2026-07 시점 보고이고 특정 과제 세트 기준이다. 모델이 바뀌면 재측정 대상이다.

## 함정

- ⚠️ **에이전트 정의는 세션 시작 시점에 로드된다.** 새로 만든 에이전트는 그 세션에서 호출되지 않고
  "해당 타입 없음" 으로 실패한다. 만든 직후 쓰려면 재시작해야 한다.
- ⚠️ **라우팅 규칙을 문서에 적어두는 것만으로는 안 돈다.** 자동 발동이 막혀 있는 형태로 배포된
  라우터는 사용자가 매번 명시적으로 호출해야 하고, 그래서 설치해 두고 사용량 0 이 되기 쉽다.
  자동으로 굴리려면 항상 로드되는 전역 지침 쪽에 규칙을 두는 편이 확실하다.
- 💡 위 두 가지 때문에, "프리셋 에이전트 + 전역 지침 한 줄" 조합이 "라우터 하나" 보다 실제로는 잘 돈다.
  전역 지침은 매 세션 자동 로드되고, 프리셋은 티어를 물고 있다.
