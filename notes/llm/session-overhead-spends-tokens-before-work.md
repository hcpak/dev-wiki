# 에이전트 세션의 고정 오버헤드는 첫 질문 전에 이미 토큰을 쓴다

> 에이전트 CLI 는 세션을 열 때마다 전역 지침·메모리 인덱스·훅 출력·플러그인 스킬 설명을
> 자동 주입한다. 하나하나는 작아 보이지만 조용히 누적되고, 빈 세션인데 컨텍스트의 수십 %가
> 이미 차 있는 상태로 시작하게 된다. 같은 오버헤드도 컨텍스트 창 크기에 따라 다른 %로 읽혀
> 원인 진단을 흐린다.

**상태**: 활성
**마지막 검증**: 2026-09-11

## 왜 그렇게 동작하나

- `[실측]` 세션 시작 시 자동 주입되는 것들이 고정 비용을 만든다. Claude Code 기준으로
  전역 CLAUDE.md, 자동 메모리 인덱스, SessionStart 훅의 additionalContext, 설치된 플러그인의
  스킬 설명(frontmatter description), 커스텀 서브에이전트 설명이 매 세션 올라간다.
  각각 0.5~7k 토큰이라 개별로는 눈에 안 띄고, 설치·추가 시점이 제각각이라 누적을 알아채기 어렵다.
- `[실측]` **플러그인은 쓰지 않아도 비용을 낸다.** 스킬의 본문은 호출 시 로드되지만
  트리거용 설명문은 전부 상주한다. 한 번도 안 쓴 플러그인 2개가 ~2.3k 토큰을 차지하고 있었다.
- `[실측]` **지연 로드(deferred) 도구는 예외다.** MCP 도구 118개가 이름만 등록되고 스키마는
  호출 직전에 로드되어, 측정상 0 토큰이었다. 도구 수가 아니라 "스키마가 상주하는가"가 비용을 정한다.
- `[실측]` **활용률 %는 창 크기 상대값이다.** 같은 ~64k 오버헤드가 1M 창에서는 6%,
  200k 창에서는 ~32%로 읽힌다. "예전엔 이렇게 안 컸는데"는 오버헤드 증가일 수도,
  모델(창 크기) 변경일 수도 있으므로 %가 아니라 절대 토큰으로 비교해야 한다.
- `[추정]` 다른 에이전트 하네스(비 Claude 계열)도 상주 프롬프트 구성이 같은 패턴으로 누적될
  것이다 — 다른 도구에서는 측정해 보지 않았다.
- `[실측]` **사용량 카운터는 "누가 불렀는지"를 구분하지 않는다.** 한 플러그인의 누적 사용량이
  121회로 찍혀 있어 상시 사용 중으로 보였는데, 실제로는 그 플러그인이 세션 시작 훅을 제공하고
  있어서 **세션이 열릴 때마다 자동으로 1씩 오른 것**이었다. 같은 기간 기록을 뒤져 보니 사람이나
  모델이 그 기능을 호출한 적은 0회였다. 정리 대상을 카운터로만 고르면 "많이 쓰는 것"으로 오인해
  남기게 된다 — 카운터는 자동 실행 경로를 걷어낸 뒤에 봐야 한다.

## 확인하는 방법

Claude Code 에서는 `/context` 가 카테고리별 분해를 보여준다.

```
$ /context
Tokens: 64.3k / 1m (6%)
System prompt: 3.9k   System tools: 16.5k   Custom agents: 2.2k
Memory files: 8.4k    Skills: 5.5k          Messages: 27.9k
MCP tools: 118 tools · 0 tokens (loaded on-demand)
```

플러그인별 예상 비용은 설치 전에 `claude plugin details <이름>` 으로 볼 수 있다.

## 이 노트가 틀렸다면

- 플러그인·훅·메모리를 모두 비활성화한 새 세션의 시작 토큰이 그대로라면
  → 오버헤드의 원인이 주입물이 아니라는 뜻이고 이 노트의 처방(주입물 정리)은 무효다
- `/context` 에서 지연 로드 MCP 도구가 스키마 크기에 비례한 토큰을 차지한다면
  → "이름만 등록되면 0에 가깝다"는 주장이 틀렸거나 지연 로드가 꺼진 구성이다
- 동일 구성으로 창 크기가 다른 모델을 열었는데 활용률 %가 같다면
  → %가 창 상대값이라는 주장이 틀렸다

## 적용 범위

- Claude Code 2026-08 시점 동작 기준. `/context` 분해 항목·지연 로드 여부는 버전에 따라 다를 수 있다
- 훅 주입물은 SessionStart 계열 훅이 additionalContext 를 반환하는 구성에서만 해당

## 함정

- ⚠️ 오버헤드는 한 번에 커지지 않는다. 플러그인 설치·메모리 추가·훅 신설이 몇 주에 걸쳐
  일어나서 "언제부터 이랬지"가 된다. 원인 조사는 설치 일자(플러그인 메타데이터)와
  파일 생성 일자를 시간순으로 늘어놓는 것이 빨랐다
- ⚠️ 인덱스성 주입물(메모리 인덱스, 위키 인덱스)을 줄일 때는 요약을 짧게 쓰는 것보다
  **원문으로 보내는 포인터만 남기는** 쪽이 안전하다 — 인덱스에 결론을 적으면 원문과 어긋난다
  ([[summary-index-drift]] 참고)
- ⚠️ **"줄일 수 있다" 와 "줄일 가치가 있다" 는 다르다.** 상주 인덱스를 한 줄로 축약해 아낄 양이
  약 1.2k 토큰이었는데 창이 1M 이라 0.12% 였다. 절대 토큰으로 비교하라는 위 규칙은 **원인 진단용**이고,
  **조치 여부는 창 대비 비율로 판단한다.** 창이 넓어질수록 정리의 실익은 사라지고 부작용(회상 신호
  손실·리뷰 비용)만 남는다.
- 💡 진단 순서: `/context` 로 카테고리 특정 → 카테고리별로 "매 세션 올라가는 파일"의
  바이트 수를 실측 → 최근 변경분부터 제거
