# birthtime 은 "언제 만들어졌나" 를 알려주지 않는다

> 파일을 원자적으로 교체하는 도구는 새 inode 를 만들고 rename 한다. 그래서 내용만 고쳐도
> `st_birthtime` 이 갱신된다. "새로 만든 파일" 과 "수정한 파일" 을 이 값으로 구분할 수 없다.

## 왜 그렇게 동작하나

macOS(APFS/HFS+)와 일부 리눅스 파일시스템은 inode 에 생성 시각을 따로 저장한다. `mtime` 과 달리
touch 로 바꿀 수 없어서 "진짜 만들어진 시점" 처럼 보인다.

문제는 **안전하게 쓰는 도구들이 대부분 제자리 수정을 하지 않는다**는 것이다. 흔한 구현은 이렇다.

```
1. 같은 디렉토리에 임시 파일을 만든다      ← 여기서 새 inode 가 생김
2. 새 내용을 전부 쓴다
3. 임시 파일을 원본 이름으로 rename 한다   ← 원본 inode 는 버려짐
```

이렇게 하면 쓰다가 죽어도 원본이 반쯤 망가진 상태로 남지 않는다. 대신 **파일의 정체성이 매번 바뀐다.**
경로는 그대로지만 inode 는 새것이고, 새 inode 의 birthtime 은 방금이다.

에디터·포매터·설정 관리 도구·언어 런타임의 "안전한 쓰기" 헬퍼 대부분이 이 방식이다.

## 확인하는 방법

inode 번호를 같이 보면 교체 여부가 바로 드러난다.

```bash
stat -f '%i %SB %Sm %N' <파일>     # inode, birth, mtime, 이름 (macOS)
```

수정 전후로 첫 번째 숫자가 바뀌면 제자리 수정이 아니라 교체다.

```
12345678 Aug 11 09:12:03 Aug 11 09:12:03 conf.yaml    # 수정 전
12349999 Aug 12 19:31:39 Aug 12 19:31:39 conf.yaml    # 내용만 고쳤는데 둘 다 바뀜
```

리눅스는 `stat --format='%i %W %Y %n'` 을 쓰고, `%W` 가 `0` 이면 그 파일시스템이 생성 시각을
아예 저장하지 않는 것이다(ext4 는 커널·도구 버전에 따라 안 나올 수 있다).

## 함정

- **"세션 중에 생긴 파일만 고르기" 같은 필터가 조용히 무력화된다.** 조건이 항상 참이 되므로
  에러 없이 전부 통과한다. 필터가 없는 것과 결과가 같은데, 코드에는 필터가 있어서 눈치채기 어렵다.
- ⚠️ `mtime` 으로 대신할 수 없다. 같은 이유로 둘 다 "마지막에 손댄 시각" 으로 수렴한다.
- 신규 생성 여부가 정말 필요하면 **파일 메타데이터가 아니라 만든 쪽의 기록**을 봐야 한다.
  생성 도구의 로그, 작업 이력, 또는 미리 찍어둔 스냅샷과의 차집합.
- 💡 반대로 이 성질을 이용할 수도 있다. inode 가 바뀌었는지 보면 **누가 제자리 수정을 했고
  누가 통째로 갈아치웠는지** 구분된다. 파일을 열어둔 프로세스가 갱신 내용을 못 보는 현상
  (열린 fd 는 옛 inode 를 계속 가리킨다)도 같은 원인이다.

## 관련

- 파일을 감시하는 쪽에서는 rename 교체가 "삭제 후 생성" 이벤트로 보인다. inotify/FSEvents 기반
  감시자가 한 번의 저장에 두 번 반응하는 이유다.
