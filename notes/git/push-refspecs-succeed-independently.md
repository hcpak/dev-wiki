# 한 번의 git push 에서 refspec 들은 독립적으로 성공하고 실패한다

> `git push origin <branch> <tag>` 에서 브랜치가 거부돼도 **태그는 올라간다.** 명령의 exit code
> 는 실패인데 일부 ref 는 이미 원격에 반영된 상태다. 태그 푸시가 CI 빌드를 트리거하는
> 환경이라면, 실패했다고 생각한 명령이 의도치 않은 빌드를 이미 시작시켰을 수 있다.

**상태**: 활성
**마지막 검증**: 2026-08-20

## 왜 그렇게 동작하나

`[문서]` git push 는 기본적으로 refspec 단위 원자성이 없다. 서버는 ref 하나하나를 개별로
수용/거부하며(`receive-pack` 이 ref 별 훅을 돌림), 전체를 한 트랜잭션으로 묶으려면
`--atomic` 을 명시해야 한다.

`[실측]` 브랜치가 non-fast-forward 로 거부된 push 에서 함께 보낸 태그는 정상 반영됐다.
태그는 기존 원격 태그와 충돌하지 않는 한 fast-forward 검사가 없기 때문이다. 그 태그가
CI 의 빌드 트리거였고, 리베이스 전의 낡은 커밋을 가리키고 있어서 — **의도한 내용과 다른
빌드가 시작**됐다. 빌드 취소 → 원격 태그 삭제 → 재태깅으로 수습했다.

## 확인하는 방법

push 출력을 ref 별로 읽는다. exit code 는 "하나라도 실패했는가" 만 알려준다.

```
$ git push origin releases/x 1.2.3
 ! [rejected]        releases/x -> releases/x (non-fast-forward)
 * [new tag]         1.2.3 -> 1.2.3        ← 이미 올라갔다
error: failed to push some refs to '...'
$ echo $?
1
```

## 이 노트가 틀렸다면

- `--atomic` 없이도 한 ref 거부 시 **모든 ref 가 함께 거부**되는 서버 관측 → 그 서버는
  수신 훅/설정으로 원자성을 강제하는 것 — "서버에 따라 다름" 으로 적용 범위 축소

## 적용 범위

git 기본 동작 + GitHub(Enterprise 포함) 실측. `receive.advertiseAtomic`/사전 수신 훅으로
원자성을 강제한 서버는 다를 수 있다.

## 함정

- ⚠️ push 가 "실패" 로 끝났다고 원격이 안 바뀌었다고 판단하지 말 것 — ref 별 상태 줄을 읽거나
  `git ls-remote` 로 원격을 확인한다.
- ⚠️ 태그 트리거 CI 에서는 낡은 커밋의 태그가 잠깐 존재한 것만으로 빌드가 돈다. 태그를 지워도
  이미 시작된 빌드는 계속되고, 산출물(패키지 버전)은 회수되지 않는다.
- 💡 브랜치와 태그를 함께 밀지 않는다: 브랜치 push → 성공 확인 → 태그 push. 묶어야 하면
  `git push --atomic`.
